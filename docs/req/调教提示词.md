# 调教提示词

> 这一篇只有一条总纲，其余都是它的展开。

## R31 · 可能进入后续 context 的产品内容可审查、可修改

用户能审查和修改那些会作为**产品内容**进入后续 context 的东西：正文、状态、
设定，以及可编排的提示词文案。不只是那几段通常被叫作“提示词”的文字——

| 也算 | 例子 |
|---|---|
| 工具描述 | 模型照着它决定调不调、怎么填参数 |
| 附属提示词 | 追加输入的措辞、空回催促、一段戏演完时的追问 |
| 渲染文案 | `（尚无记录）`、`（{chars} 字，用 state_query 展开）` |

**不包括执行记录与协议流量**：thinking、tool call、tool result 与运行时错误保持只读，
不进入提示词编辑器。它们只在当前 turn 内供执行使用；打断挂起时为了恢复而暂存，
turn 完成、放弃或失败后不进入节点，也不进入后续 turn 的 context。开发者 trace
可以另行留存完整交换，但 trace 不是模型上下文。

**为什么把后三类也圈进来**：它们量不大但每轮都进上下文，其中几条是**明确的操作
指令**——改了工具名却忘了改它们，模型会去调一个不存在的工具。

## R32 · 所见即所得

编辑器里显示的那段文字，**必须就是模型收到的那段**。

**不包括**：系统在保存后自动加标签、自动包裹、自动补格式。每替用户多做一件事，
"看到的"和"发出去的"就差一点，而审查的前提正是这两者相同。

要标签就用户自己写进去——那时它可见、可编、可删。

## R33 · 提示词管理一直开着

不由开发者模式门控。**这台服务的部署方就是用户自己**，而调提示词是这个项目里最
日常的动作，把最日常的入口藏在一个"给查问题用"的开关后面，方向是反的。

## R34 · 一节的位置能拖，加一节不用改代码

每份提示词是一列可拖动排序的节。调位置就是拖一下，加一节就是加一条。

节分三类：**正文可编的**、**只有位置可调的**（内容是系统算出来的数据）、
**几档里选一档的**（每一档的正文都能改）。

## R35 · 改坏了要当场拒绝，不能等到下一轮 500

保存前系统先试装配一遍。装不出来就拒绝保存，并**点名是哪一节坏了**。

**为什么**：否则改坏一个字，下一轮生成直接 500，而错误信息离原因很远。

## R54 · 提示词按完整套装管理

提示词会同时存在多套。用户能复制当前套装、改名、切换与删除自建套装；每一套都完整
包含所有 agent 与单次调用的 YAML，不靠「默认套装 + 若干覆盖」拼出实际内容。

当前套装是**服务级选择**。切换只影响之后开始的 turn；已经运行或挂起的 turn 继续使用
开始时冻结的整套快照。套装不绑定 session、worldbook 或单轮输入。

**为什么**：稀疏覆盖会让一份实际提示词分散在继承链的几个目录里，界面显示和磁盘上
任一文件都不再是完整真相；session 级选择又会把服务配置重新降回故事内容。

---

## 一个已知代价

choice 住在提示词里，意味着**同一台服务上两局故事不能有不同的控制取值**，
不只文风如此，输入处理、剧情控制权、抢话规则与三项密度选择也一样。

这是"取值只有一处"的定义本身带来的，不是疏漏。不同 session 仍不能同时使用不同
取值；要换配置就切换当前提示词套装——那是服务级动作，不是每个 session 或 turn 的选项。
