# 用户输入的处理

> **回答**：用户打进来的一句话怎么被接住，以及要避免哪几种失败。
>
> **不回答**：控制维度有哪几档（见 [Prompting.md](Prompting.md)）、
> 插话与打断的时机（见 [Branching.md](Branching.md) S48–S50）。

## 全貌

airp 相对批量写作最本质的差异：**批量写作里没有人在环内**，内容规格只能由系统自产；
airp 里用户持续供给输入，**且输入形态与完整度差异极大**。

### 不做显式分类

真实输入是混合的——一句话里可能同时含有角色行为、戏外要求和对既有设定的修改。
**分类是有损的，且失败是静默的**：归错类不会报错，只会产出"看起来合理但不是要的东西"。
即使分类正确，**分类也不直接给出处理方式——分类不是决策**。

真正有用的是那个**连续量：输入的规格度**。它决定 director 要补多少：
输入已足够具体时补全工作量应为零（再走一遍是把它压缩再解压，纯损失），
只给方向时最大。**长循环自主创作是极限情形**——完全没有用户输入，细纲必须自产。

### 设计目标是「避免哪些失败」，不是「怎么归类」

四个已知的失败（举例，非穷举）：

| | 失败 | 描述 |
|---|---|---|
| **P1** | 漏转述 | 用户给出的内容本该进正文，却被当成前提悄悄跳过 |
| **P2** | 覆盖不全 | 用户指令只被执行了一半 |
| **P3** | 控制权移交未被识别 | 输入里的"空白"本该被读作授权，却被读作无事发生 |
| **P4** | 用世界规则悄悄换掉用户的动作 | 见 [S106](#s106) |

前三者的共同结构：**用户输入与模型输出之间的关系没有被正确建立。**

### S106 · 动作是锚点，结果归世界

**服务** [R8](../req/推进剧情.md)

**规格** 用户写出的动作**不能省略、不能换成别的动作**。
但结果由世界决定：冷却没过、钱不够、东西用完、对方先动了手，都可以让它落空。

**落空必须写得可见、有据**——写清他确实试了、以及为什么没成。

**不做** 偷偷换成一个能成的动作；不做当作他没做过。

**为什么** 转述规则（用户动作是锚点）与世界规则（否定项、冷却、余额）会**正面冲突**。
实测：用户写「我再来一记御剑斩」，而它还在冷却——**两条规则都成立，指向相反。**

模型当时选对了，**但设计里从没规定过这件事——它是蒙对的**，
而 grader 把它判成了推演错。**这类"两条规则都对但打架"的地方，不写下来就等于交给运气。**

### S107 · 排队逐条消费，不得打包

**服务** [R7](../req/推进剧情.md)

**规格** 队列是 FIFO，**每条输入独立成一个 run**。
用户应能看到队列里待处理的输入。

**不做** 把几条排队输入合并成一次。

**为什么** **角色扮演里每个用户动作都需要独立的世界响应。** 用户连发
「我推开门」/「我环顾四周」/「我叫了一声」，打包会变成"你推开门环顾四周叫了一声，
然后……"——**跳过了中间信息，而推开门看到什么本应影响要不要叫。**

打包本质上是 P1 / P2 的一个变体：用户输入被压缩处理。
它还会破坏「每轮一份状态增量」——打包后只剩一个，中间状态全丢。

**验收** `test_ordinary_submit_still_chains_onto_the_active_leaf`

### S108 · 队列非空时暂停自主推进

**服务** [R7](../req/推进剧情.md)

**规格** **用户输入优先于模型自主推进。** 倾向定死，不做成可配置。

**为什么** 否则控制权高时模型自行跑了好几轮，**用户排队的输入被消费时已经过时。**

**验收** `test_no_goal_means_no_autocontinue`

### S109 · 元操作不进模型上下文

**服务** [R20](../req/回头与改写.md)

**规格** 回滚、分支、停止、改设定进控制面，**不进模型上下文**。

**不做** 把内容输入再分成"戏内"与"戏外引导"两条通道——
它等价于「输入处理」那个维度的三档划分，既已做成显式控制就不必再设一层通道。

**验收** `test_ordinary_submit_still_chains_onto_the_active_leaf`

### S110 · 不校验输出是否完整消费了输入

**服务** —（能力边界）

**规格** **不做这项检查。**

**为什么** 它是语义判断，代码做不了。唯一的实现路径随抽象规格一起作废。
eval 时分析 trace 本就包含它。

## 一条残留成本，诚实记下来

**显式化并没有消除推断，只是把它缩小了。**

原先是"这句话属于哪一类"，现在是"设置与输入冲突时谁赢"。
选「显式优先」等于把这个残留问题也一并消除——
**代价是可能出现「我明明写了详细剧情它却全改了」这类体验。**

## 与流式的关系

**不为保住逐 token 流式而扭曲 agent 结构**——这一条没变，它反对的是**为流式改结构**。

**但流式作为输出通道加回来了**，不动任何结构：四个 agent 的顺序、工具循环、契约、
重放全都不变，agent 那侧根本不知道自己在不在流。

所以「用户可感延迟 = 整条工作链的串行时间」**已经不成立**：
实测**第一片 1.1 秒到，整轮 362 秒**。等待的形状变了——
从"盯着一个转圈的图标"变成"看着它一句句写出来"。

token 成本仍是另一个独立的预算，与延迟无关。
