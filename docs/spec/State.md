# 状态

> **回答**：世界的当前样子存成什么形状、谁能改它、记什么不记什么。
>
> **不回答**：它怎么被检索（见 [Retrieval.md](Retrieval.md)）、谁写它
> （见 [Architecture.md](Architecture.md) S7）、切分支时怎么重算（见 [Branching.md](Branching.md)）。

## 全貌

一句话：**有限建模、结构化存储、模型判断、代码只管形状不管内容。**

状态是**派生数据，不落盘**——落盘会导致用户编辑了快照却被重建覆盖。
权威是每个节点上的那份增量，当前状态是沿路径重放的结果。

### S30 · 存储层不预设任何维度

**服务** [R22](../req/回头与改写.md)

**规格** 键自由命名，值是任意 JSON。时间、地点、角色属性都没有预设字段。

**不做** 「在场 / 时间 / 地点 / 谁知道什么」这样一层固定核心 schema。

**为什么** 这类 schema **在原理上就定不下来**——"下午一点"、"是晚上"、"过了一个月"
在不同情境下影响完全不同；地点可以是某国家、某酒店、"婚礼进行中"；知情不是每个
故事都要维护。**加字段只是把猜测挪到更深一层。**

错误不在字段选得不好，在这层 schema 本身。曾经的三轮修补（知情建成关系矩阵、
角色档案与在场分离、时间分绝对相对）**同样作废**：它们都在修字段。

**验收** `test_any_shape_of_time_is_expressible` · `test_any_granularity_of_place_is_expressible` · `test_arbitrary_character_attributes` · `test_story_without_knowledge_tracking_is_fine`

### S31 · 层次用 JSON 嵌套，不用点分键名

**服务** [R22](../req/回头与改写.md)

**规格** 状态是一棵嵌套的 JSON 树。寻址**一律用路径数组**（`["林", "知情"]`）。
点分只保留在给人看的标签里（`林 › 知情`），**那不是语法**。

**不做** `林.在场` 这样的平铺键 + 点号分组。

**为什么** 三条，最硬的是第三条——

1. 点分是一套**要教的私有语法**，而 JSON 自带的嵌套模型模型本来就会。
2. 分组只在渲染时发生、存储仍是平的，于是"某个角色名下有哪些东西"代码得现算，
   **键里出现真正的点号还会算错**。
3. **按层级控制展开根本做不了**——平铺结构里没有"层"，只能按值的字符数藏，
   而字符数和"这一块要不要给"没有关系。嵌套之后深度是现成的。

点号刚被取消结构含义，再拿它当寻址语法等于把刚拆掉的歧义装回去。

**验收** `test_structure_is_the_json_structure` · `test_append_and_remove_address_nested_lists`

### S32 · 写入语义只有三种，`set` 是深合并

**服务** [R20](../req/回头与改写.md) [R23](../req/回头与改写.md)

**规格**

| | 语义 |
|---|---|
| `set` | **深合并**——只动补丁里提到的键。叶子为 `null` 删除那棵子树 |
| `append` | 追加去重。键不存在时创建一个列表 |
| `remove` | 从清单里拿掉几项。作用在标量上等于删掉那个键 |

套用顺序是 **set → remove → append**，所以"换掉一项"能在一次写入里表达。

**不做** 让 `set` 整枝替换。改一个角色的一项属性不该重发整个角色——
**整体重发正是清单被拍平的老路**。

**为什么** `remove` 是补的：原先只有增没有减，去掉一项只能 `set` 整个列表。
实测模型干脆绕开了结构——把 `["青锋剑", "止血符 ×2"]` 写回成
`"青锋剑、止血符 ×4"`，**清单一次性塌成字符串且不可逆**。

**这个缺口在纯文学场景里永远看不见**：那里的清单（知情、经历过的事）天然只增不减。
数据化的世界才暴露它。这是一条方法论：**判据和语义都要拿一个反向的世界压一遍。**

**验收** `test_set_overwrites_and_none_deletes` · `test_a_set_merges_deeply_instead_of_replacing_the_whole_branch` · `test_a_null_leaf_deletes_that_subtree` · `test_append_accumulates_and_dedupes` · `test_remove_takes_items_off_a_list` · `test_remove_then_append_swaps_one_item_in_a_single_write` · `test_remove_on_a_scalar_deletes_the_key` · `test_unmentioned_keys_are_untouched`

### S33 · 状态注入用 JSON，不加任何形状标记

**服务** [R31](../req/调教提示词.md)

**规格** 全量键名 + 体量小的值内联；**长的字符串**只给体量，让模型用
`state_query` 展开。渲染成 JSON。

**不做** 在值那一侧加形状标记（曾经清单渲染成 `清单：青锋剑、止血符 ×2`）；
不做长清单的隐藏——长清单该做的是**拆键**。

**为什么** 那个 `清单：` 前缀本来是为了让清单和字符串长得不一样。
**但实测模型把它当成了值的开头抄了回来**，写回一个以那四个字打头的字符串——
形状照样塌，还多了四个字的垃圾。

判据由此清楚：**形状标记只要落在值这一侧，就是可抄的。**

JSON 从根上消掉它：`[…]` 不是 `"…"`、`3` 不是 `"3"`、`{}` 不是 `""`，
一个标记都不用，而且**和 `state_write` 的参数是同一套写法**——模型读到什么形状
就写回什么形状，中间没有一次翻译。

**验收** `test_structure_is_the_json_structure` · `test_state_write_says_what_to_record`

### S34 · 记什么：先过门槛，再分两类

**服务** [R22](../req/回头与改写.md)

**规格** 门槛：**需要随时看见它，且不值得为它去翻前情。**

过了门槛之后分两类，**忘了的后果完全不同**：

| | 忘了会怎样 | 例子 |
|---|---|---|
| **约束类** | 写出**不可能发生**的事 | 谁死了、谁不在场、受了什么伤、还剩几块钱、法术还在冷却 |
| **悬置类** | 不出错，但**烂尾** | 搁在桌上的枪、许下的承诺、没答的问题、撂下的狠话 |

悬置类的判据要窄：**有人特意让它出现，而它还没有下文。**
桌上的杯子不记；被人拿起来又放下的那个杯子才可能要记。

**兑现即删。** 于是状态里的悬置项恒等于「当前还欠着的账」——
一份会自己清空的待办，不是只增不减的清单。

**为什么** **悬置类最容易漏，恰恰因为它什么也不禁止。** 枪挂在墙上，不写它照样
写得下去——单靠"会不会出逻辑错误"这条判据，它必然被丢掉。这是判据的缺口，
不是模型的失误。

它还有个连带作用：**把一部分伏笔从检索问题变成了记账问题**。有意埋的伏笔进状态；
只有"当时无人在意、后来才变关键"的细节才真正需要翻原文。

**验收** `test_state_write_says_what_to_record`

### S35 · 不记什么：存续时长不是判据

**服务** [R22](../req/回头与改写.md)

**规格** 每轮必过的自检是**「下一轮开始时，这条还成立吗」**。
画面归正文，状态只留画面**留下的东西**。

另外两条否定：**不记「未明」「不确定」**（没记的本来就是未知）；
**不记来源**（"名字由陈屿说出"属于某人的知情，不属于被说的那个东西）。

**不做** 用「存续时长」当判据。

**为什么** 曾经的时态判据（"记的是下一轮世界什么样，不是这一轮发生了什么"）
排得掉情节复述，**但排不掉记得过细**——`照片.朝向: 正面朝上` 完美通过时态测试。
缺的是**用处**这一维。

"只在这一两轮内有意义的就不记"这条经验也是错的：

| | 存续 | 该记吗 |
|---|---|---|
| `沈砚.冷却: 御剑斩还剩 2 回合` | 两轮 | **必须**——漏了就会重复放技能 |
| `照片.朝向: 正面朝上` | 永远 | 不必——写岔了没人算得出矛盾 |

判据里早就点名禁过物件朝向这类，**说明光加禁令没用**；换成每轮必过的自检才有效，
复跑确认这一类整类消失。

**验收** `test_state_write_says_what_to_record`

### S36 · 状态是 history 的捷径，不是第二份记录

**服务** [R22](../req/回头与改写.md)

**规格** 信息本体在 history 里。状态把"每轮都要用、又不该每次回头翻"的那几条
拎到眼前。

三个推论：判据是**双条件**的（既约束后面能写什么，又值得随时看见）；
**删键不等于丢信息**，所以状态该保持短、`set null` 才成为一个模型敢用的动作；
**结构化靠提示词鼓励，不靠 schema 强制**。

**为什么** 这条定位撑起上面全部判据。它还修正了写入侧的风险估计：细纲里写了但没进
状态的，**可以从 history 回捞**；只有那些只存在于正文里的事实才真正不可自愈。

**验收** `test_empty_delta_is_legal_and_noop` · `test_set_overwrites_and_none_deletes`

### S37 · 初始状态在故事开始时冻结

**服务** [R2](../req/开局与设定.md)（"故事一旦开始，设定的哪一半就冻结了"）

**规格** 设定里的初始状态在**第一轮开始时**快照进 `Session.initial_state`。
开始之前仍然现算。它是一切分支共同的重放起点。

**不做** 一直现算。

**为什么** 曾经的说法是"改了影响所有分支，同改角色卡，是对的"——**那个类比不成立**：
改角色卡改的是设定，而这里改的是**已经发生过的剧情所依赖的事实**。
第五轮写着「她掏出钥匙」而钥匙来自初始状态，把它删掉，那一轮就凭空多了一把不存在的
钥匙，**且没有任何地方会报错**。

**验收** `test_the_initial_state_freezes_once_the_story_starts` · `test_state_entries_become_the_replay_base`

### S38 · 代码不做任何内容判断

**服务** —（能力边界）

**规格** 代码这一侧**一类检查都不剩**。内容判断全交给模型，程序只做
**eval 采样标记**（"正文很长但增量为空"、"正文明显短于展开密度"），
**标记从不影响运行时行为**。

**不做** 四类曾设想过的结构性交叉比对——

| 设想 | 为何做不了 |
|---|---|
| 时间单调 | 时间是自然语言（"傍晚"、"第二天"） |
| 说话者 ⊆ 在场 | 从正文抽说话者是语义工作 |
| 地点可达 | 需要拓扑图，而地点只是字符串 |
| 知情者 ⊆ 在场 | **不成立**——信息可经转述、书信、监听获得 |

**为什么** 硬做只会得到假警报，**而假警报比不检查更糟**。

还有一个必须避免的错觉：把 `关系[A][B] = 决裂` 存成结构化字段再用代码读它比对它，
看上去像"代码判定"——**但那个值本就是模型写进去的**。语义判断发生在写入时，
代码检查发生在读取时，后者只是一次查表。

**验收** `test_long_prose_with_empty_delta_is_flagged` · `test_prose_barely_longer_than_outline_is_flagged` · `test_properly_expanded_prose_is_not_flagged`

### S39 · 键名漂移只报「裸键 vs 同名带前缀键」

**服务** —（开发期采样）

**规格** 采样器只认这一种形状：`冷却` 与 `沈砚.冷却` 并存。

**不做** 判 `位置` 与 `地点` 这类近义漂移——代码判不了，仍然只能靠把已有键列表
回给模型。

**为什么** 判别式必须这么窄：`林昭.知情` 与 `陈屿.知情` 共享词尾却**都是对的**，
两边都带前缀就不是歧义。**误报会让标记立刻失去价值。**

提示词里已经写着"新建键之前先看有没有已在说同一件事的键"，**没拦住**——
实测模型在 `沈砚.冷却` 已存在时另起裸键 `冷却`，两键并存值还不一样，
下一轮它自己发现并删掉，但中间那一轮是脏的。

### S40 · 用户改状态：改指令与改结果，都作用在当轮增量上

**服务** [R21](../req/回头与改写.md) [R23](../req/回头与改写.md)

**规格**

| 操作 | 用户改的 | 系统怎么落 |
|---|---|---|
| **改指令** | 那一轮的 `set` / `append` / `remove` | **整份替换**增量 |
| **改结果** | 那一轮**之后**的状态树 | 服务端 `diff(before, after)` 反推成增量 |

三条约束：**改指令是整份替换不是只换 `set`**；**求差在服务端做**，
所以"权威是增量"这句话不会被破坏；**`diff` 只产出 `set`**。

两个字段**只能给一个**，一起给当场报错。

**不做** 让 `diff` 猜 `append`。从两棵树看不出用户心里想的是"追加一项"还是
"换成这个列表"，猜错了下游重放就不一样——要表达追加走「改指令」。

也不做「改历史会连锁」之类的警告：下游照常重放就是 event-sourced 的正常行为。

**为什么** 一起给时"我改了结果，它却按指令存了"是**查不出来的那种错**。

**验收** `test_diff_is_the_delta_that_turns_before_into_after` · `test_diff_only_mentions_what_changed` · `test_diff_expresses_a_deletion_as_a_null_leaf` · `test_diff_never_guesses_append` · `test_diff_creates_an_empty_branch_that_was_not_there` · `test_user_edit_rewrites_node_directly` · `test_editing_an_older_node_keeps_the_state_at_the_leaf`

### S41 · 编辑直接改写节点数据，不做依赖检查

**服务** [R20](../req/回头与改写.md)

**规格** 用户改细纲、正文、状态都是直接改写那个节点，**不检查下游**。

**不做** "插入一个只含增量的新节点"来保护不可变性。

**为什么** 乐观假设用户只改最新输出，此时本无下游。为一个乐观假设下不存在的问题
增加复杂度，也不符合常见 AI chat 的编辑语义。

**验收** `test_user_edit_rewrites_node_directly` · `test_editing_outline_invalidates_cached_summary`
