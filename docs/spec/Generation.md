# director / writer 为什么这么拆

> **回答**：这一刀为什么切在这里，换一刀会怎样。这是整个系统最核心的一条论证。
>
> **不回答**：拆完之后的组件与时序（见 [Architecture.md](Architecture.md)）。

## 论证

判据是 [Principles.md](../Principles.md) P1–P3：多 agent 唯一不可替代的收益是
**上下文隔离**，所以问的不是"该不该有 director"，而是——

> 为了产出最终给用户看的正文，需要哪些 context？**这些 context 可不可分？**

方法是先枚举全部 context，再看某种切法下两侧是否有实质差异。
**同一组工作在不同切法下结论可以相反**，下面两张表就是。

### 切法一：两侧都读正文 —— 不可分

| context | 决定"写什么" | 决定"怎么写" |
|---|---|---|
| 正文上文 | ✓ 接剧情 | ✓ 接语气 |
| 世界设定 | ✓ 什么合理 | ✓ 描写要准 |
| 用户指令 | ✓ | ✓ 转述需原文措辞 |
| 节奏 / 基调 | ✓ 涵盖多少事件 | ✓ 句式与段落长度 |
| 文风 | ✗ | ✓ |
| 角色语言习惯 | ✗ | ✓ |

**共享项占体量的绝大部分，独占项都小。** 拆分不能让任何一方的 context 变小，
只是两边都带着同一大坨、各自多一小块。

套 P2 的判据表：director 入参是"共享的一大坨"，出参是一份 brief——**多入少出，
不要拆**，而且这里的压缩是品味类的，没有验证器。

**此切法下结论是合并。**

### 切法二：director 只读细纲不读正文 —— 可分

| context | director | writer | 体量 |
|---|---|---|---|
| 细纲历史 | ✓ | ✗ | 中 |
| 正文上文 | ✗ | ✓ 衔接 | **大** |
| 世界设定 | ✓ | ✗ 细节已在细纲里 | **大** |
| 状态 | ✓ | ✗ | 小 |
| 用户指令 | ✓ | ✗ 已在细纲里 | 小 |
| 叙事节奏 | ✓ | ✗ 细纲的事件密度已编码它 | 小 |
| 文风 | ✗ | ✓ | **大** |
| 角色语言习惯 | ✗ | ✓ | **大** |

**几乎无共享项。这是真正的可分。**

前提是**细纲到正文的映射无歧义**，即细纲要足够细。极限形态就是：
director 在不约束文风的情况下写出一篇文章，writer 再按文风改写它。

### 这一刀独有的收益

**细纲比正文压缩，所以同样的 token 预算下 director 能看长得多的历史。**
细纲约为正文的 1/5，director 就能覆盖五倍跨度的前情。

这对长程一致性是直接的、不需要额外机制的收益，甚至部分替代了状态的作用——
很多"她之前做过什么"的问题，读细纲历史就够。**合并方案拿不到这个收益**，
因为合并后只有一份上下文，压缩与否是全局的。

### 成本

director 写一遍近全长的文章，writer 再改写一遍，**输出 token 约 2 倍**，
明显贵于"短规格 + 正文"。

但这笔交易是自洽的：短规格便宜，代价是品味类的有损压缩；细纲=文章几乎无损，
代价是 token。P7 主张预算应几乎全压在**无验证器的那条边**上——这里正是在按它花钱。

### S13 · 中间量是无文风约束的文章，不是抽象规格

**服务** [R7](../req/推进剧情.md)

**规格** director 的产出是一篇散文，**不预设任何字段格式**。

**不做** 让 director 产出一个结构化对象（人物 / 冲突 / 结局这样的 schema）。

**为什么** 散文形态解掉了抽象规格方案的两个致命伤：**不依赖任何未经证实的写作
理论**；模型不必把"想写什么"翻译成一个符合 schema 的对象，**没有元层任务**。
后者正是抽象规格与 P10（开放判断降级为受约束的选择）冲突的根源——它反而增加了
思考负担。

**验收** `test_full_run_produces_a_node` · `test_writer_sees_prose_upstream_director_does_not`

### S14 · 篇幅只讲给 writer，director 那侧换成事件密度

**服务** [R14](../req/推进剧情.md)

**规格** 给 director 的是**事件密度**，给 writer 的才是篇幅。两侧用「事实 vs 呈现」
的对照说同一件事，并明确告诉 director「你写了它只会照抄」。

**不做** 给 director 篇幅要求。

**为什么** 实测的根因：director 的提示词同时说"产出是完整文章"并给了篇幅要求，
而**篇幅只能靠描写凑**——于是它写出成品散文，writer 除了照抄无事可做。
细纲/正文长度实测 524/526、739/753、559/544；改为事实 vs 呈现的对照后降到
214/710、217/463、240/558。

**验收** `test_prose_barely_longer_than_outline_is_flagged` · `test_properly_expanded_prose_is_not_flagged`

### S15 · 细纲不承担文风；细纲的文风缺陷不在 director 侧修

**服务** [R14](../req/推进剧情.md)

**规格** 细纲的用词、句长、标点、段落切法都只是把事实交代清楚的临时手段。
**它写得干巴、重复、破折号成灾，都不该由 director 那边去治。**
若正文跟着细纲的腔调走，那是 writer 的缺陷——修在 writer 侧，明写「细纲怎么写的，
与正文怎么写无关」。

**不做** 为了正文好看去清洗 director 的提示词。

**为什么** 那是在错误的层上优化，而且会把文风职责重新拆散到两个 agent 上。
实测支持：把 director 提示词的破折号从 5.84‰ 清到 0.90‰，细纲跟着降 36%
（4.39 → 2.82），**而正文纹丝不动（5.42 → 5.38）**——writer 本来就没在跟细纲的
文风走。

**验收** `test_director_never_sees_style_or_prose` · `test_style_and_prose_never_reach_the_director`

### S16 · 多候选做在细纲层，不在正文层

**服务** [R12](../req/推进剧情.md)

**规格** 要给用户几个走向选时，产出的是几份**细纲**，选定后只跑一次 writer。

**不做** 生成三段成品正文让用户挑。

**为什么** 三份细纲比三段成品便宜，用户读走向也比读全文快，而且**用户要控制的是
走向不是文笔**。

**验收** `test_a_question_takes_exactly_three_options`

### S17 · director 拿不到角色的原话，接受这个限制

**服务** —（这是一条明说的能力边界）

**规格** 措辞由 writer 定，**原话只存在于正文里**。director 回答不了"她上次说的是
『永远』还是『暂时』"这类需要精确引用的问题。**不开机制口子。**

**不做** 两条都不做——

- 开一个窄查询 `text.quote(run_id, hint)`：几十字严格说不违反隔离，但**口子一开
  director 会频繁调用，逐渐等价于读正文**。
- 让 writer 把关键台词回写进细纲：加重 writer 职责，与"纯渲染"定位冲突。

**为什么** 缓解靠提示词双向用力（提高 writer 对细纲的遵循度、提高 director 写细纲的
详细度：关键台词、数字、价钱、名字、期限直接写死在细纲里），出错靠用户纠正。
**不为不可自愈的边缘情况增加结构复杂度。**

**验收** `test_history_never_leaks_prose`

## 未定

**文风的结构层能不能 100% 留在 writer 侧。**

这个方案本质是两阶段生成（draft → style pass），已知失败模式是第二遍把第一遍的好
东西磨平。**此处方向有利**：第一遍不带文风约束，第二遍是在**去 AI 腔**而非加，
比反过来安全。

**残留担忧**：默认腔调写出来的东西，**结构上可能已经是 AI 味的**——三段式、
总结性收尾、对称句式。第二遍换词容易，换骨难。若成立，文风约束里的结构性部分
就必须前移到 director，而那会重新污染它的上下文。

**要什么才能定**：一次消融——同一批细纲，结构性文风约束分别放 writer 侧和两侧，
比较产出。与「细纲的粒度下限」是同一张力的两端，须一起测。
