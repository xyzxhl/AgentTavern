# director / writer 为什么这么拆

> **回答**：这一刀为什么切在这里，换一刀会怎样。
>
> **不回答**：拆完之后的组件与时序（见 [Architecture.md](Architecture.md)）。

## 论证

旧设计把「director 永远不读正文」当成拆分成立的前提，并把细纲当作跨轮历史。
这条前提已撤销：计划与成文冲突时，正文才是用户实际读到、也是故事实际发生的版本；
让任何下游继续读细纲会制造第二份叙事真相。

现行拆分靠的是**职责与调用形态**，不是两侧完全没有共享 context：

| context | director | writer |
|---|---|---|
| 正文历史 / 上文 | ✓ 接续事实、避免重复 | ✓ 保持现场、人物与行文衔接 |
| 世界设定与 state | ✓ 判断什么能发生 | ✗ 由细纲交代本轮所需事实 |
| 用户输入与控制项 | ✓ 决定本轮发生什么 | ✗ 已落实在细纲中 |
| 本轮细纲 | 产出 | ✓ 唯一任务输入 |
| 文风与角色语言习惯 | ✗ | ✓ 决定怎样呈现 |

两侧共享的是正文连续性依据，但工作不同：director 在 tool loop 中检索、推演并收束
「发生什么」；writer 在一次无工具调用中把已定事实渲染成正文。细纲是可审计的阶段边界，
也是归因「规划错」与「渲染偏离」的参照物，但只活在当前 turn。

writer 读正文上文不等于重写上文。它只用上文校准人物、现场与语气，输出必须从上文
已经到达的位置继续。director 同样要从正文历史识别已经完成的剧情阶段，避免重新安排。

### S178 · 开场白与正文 history 都是已发生边界

**服务** [R7](../req/推进剧情.md) [R53](../req/开局与设定.md)

**规格** history 中的 assistant 正文（包括选中的静态开场白）已经向用户展示，也已经在
故事中发生。director 的新细纲从最后一份正文的最后一句之后开始，只能承接其后果，不能
把其中的动作、对白、发现或场面重新安排进本轮；「转述然后推进」只转述当前顶层输入。

writer 同样把上文只作为连续性依据。即使细纲误收了上文事件，writer 也不再次渲染。

**不做** 把开场白视为等待首轮展开的素材；不靠正文相似度正则裁掉重复段落。

**为什么** 复述首先是语义规划问题，不是字符串问题。用相似度硬裁会误删有意回忆、
复现或不同视角，且无法识别改写后的重复；两层提示词守住各自职责，trace 用来归因。

**验收** `test_repetition_guards_reach_the_responsible_agents`，真实模型首轮回归检查。

### S181 · writer 把细纲终点当作本轮正文上界

**服务** [R57](../req/推进剧情.md)

**规格** writer 可以自由决定细节与呈现，但细纲列出的场景、动作、信息与结果完成后
立即结束。细纲未明确要求时，不继续写后续反应、赶路、时间跳转、下一项任务或下一幕
准备。

**不做** 用代码按字数或相似度截断；不让 writer 自己判断下一轮应发生什么。

**为什么** writer 的职责是渲染这一轮，不是把一个正确的细纲当起点继续规划。过严的
长度门禁会伤害不同文风，语义终点才是实际边界。

**验收** `test_writer_receives_the_outline_endpoint_guard`，真实模型边界回归检查。

### S183 · writer 保持一条可计算的时间线

**服务** [R59](../req/推进剧情.md)

**规格** 上文、用户输入或细纲已经给出绝对日期、经过天数或相对时间时，writer 在渲染前
先把它们对齐到同一条时间线。跨夜后的「今日／明日／次日」必须指向一致；细纲没有要求
时不另加时间跳转，不能靠含糊措辞掩盖冲突。细纲明确给出的时刻或日期本身属于剧情事实；
正文的开场时刻、终点与中间顺序都不得换成相邻时段、模糊说法或另一套日期。

**不做** 用代码正则裁正文；不强制所有故事使用日期或统一历法。

**为什么** 时间是自然语言，但已给出的相对关系仍可前后对照。正文自己冲突后，
下游只能猜一个值，state 再精确也会把猜测伪装成事实。

**验收** `test_writer_receives_the_timeline_guard`，真实模型跨夜场景回归检查。

### 收益与成本

收益是职责可以分别约束、观测和评估：director 的问题可对照输入、state 与细纲，writer
的问题可对照细纲与正文；文风无需进入 director，检索工具也无需进入 writer。代价是
两次生成调用和一份临时中间产物，而且两侧都读取部分正文，不能再声称通过细纲历史获得
数倍上下文跨度。长历史的体量问题统一交给基于正文的归段摘要解决。

### S13 · 中间量是无文风约束的文章，不是抽象规格

**服务** [R7](../req/推进剧情.md)

**规格** director 的产出是一篇散文，**不预设任何字段格式**。

**不做** 让 director 产出一个结构化对象（人物 / 冲突 / 结局这样的 schema）。

**为什么** 散文形态解掉了抽象规格方案的两个致命伤：**不依赖任何未经证实的写作
理论**；模型不必把"想写什么"翻译成一个符合 schema 的对象，**没有元层任务**。
后者正是抽象规格与 P10（开放判断降级为受约束的选择）冲突的根源——它反而增加了
思考负担。

**验收** `test_full_run_produces_a_node` · `test_a_completed_node_does_not_persist_the_outline`

### S14 · 篇幅只讲给 writer，director 那侧换成事件密度

**服务** [R14](../req/推进剧情.md)

**规格** 给 director 的是**事件密度**，给 writer 的才是篇幅。两侧用「事实 vs 呈现」
的对照说同一件事，并明确告诉 director「你写了它只会照抄」。

**不做** 给 director 篇幅要求。

**为什么** 实测的根因：director 的提示词同时说"产出是完整文章"并给了篇幅要求，
而**篇幅只能靠描写凑**——于是它写出成品散文，writer 除了照抄无事可做。
细纲/正文长度实测 524/526、739/753、559/544；改为事实 vs 呈现的对照后降到
214/710、217/463、240/558。

**验收** `test_outline_prose_length_ratio_is_not_judged_by_code`

### S15 · 细纲不承担文风；细纲的文风缺陷不在 director 侧修

**服务** [R14](../req/推进剧情.md)

**规格** 细纲的用词、句长、标点、段落切法都只是把事实交代清楚的临时手段。
**它写得干巴、重复、破折号成灾，都不该由 director 那边去治。**
若正文跟着细纲的腔调走，那是 writer 的缺陷——修在 writer 侧，明写「细纲怎么写的，
与正文怎么写无关」。

**不做** 为了正文好看去清洗 director 的提示词。

**为什么** 那是在错误的层上优化，而且会把文风职责重新拆散到两个 agent 上。
实测支持：把 director 提示词的破折号从 5.84‰ 清到 0.90‰，细纲跟着降 36%
（4.39 → 2.82），**而正文纹丝不动（5.42 → 5.38）**——writer 本来就没在跟细纲的
文风走。

**验收** `test_director_never_sees_style` · `test_style_never_reaches_the_director`

### S16 · 多候选做在细纲层，不在正文层

**服务** [R12](../req/推进剧情.md)

**规格** 要给用户几个走向选时，产出的是几份**细纲**，选定后只跑一次 writer。

**不做** 生成三段成品正文让用户挑。

**为什么** 三份细纲比三段成品便宜，用户读走向也比读全文快，而且**用户要控制的是
走向不是文笔**。

**验收** `test_a_question_takes_exactly_three_options`

## 未定

**文风的结构层能不能 100% 留在 writer 侧。**

这个方案本质是两阶段生成（draft → style pass），已知失败模式是第二遍把第一遍的好
东西磨平。**此处方向有利**：第一遍不带文风约束，第二遍是在**去 AI 腔**而非加，
比反过来安全。

**残留担忧**：默认腔调写出来的东西，**结构上可能已经是 AI 味的**——三段式、
总结性收尾、对称句式。第二遍换词容易，换骨难。若成立，文风约束里的结构性部分
就必须前移到 director，而那会重新污染它的上下文。

**要什么才能定**：一次消融——同一批细纲，结构性文风约束分别放 writer 侧和两侧，
比较产出。与「细纲的粒度下限」是同一张力的两端，须一起测。
