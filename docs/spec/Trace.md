# trace 与开发者模式

> **回答**：查问题时系统留下什么、留在哪、怎么读回来。
>
> **不回答**：开发者面板长什么样（见 [UI.md](UI.md)）、
> trace 在分支切换时的性质（见 [Branching.md](Branching.md) S47）。
>
> 这一篇是新开的——trace 与开发者模式此前散在拓扑、界面、优化三处。

## 全貌

trace 是**评估与排查的唯一数据源**，也是界面的数据源：
**界面是 trace 的投影**，不是另一份记录。

---

### S111 · 界面是 trace 的投影，两层分开

**服务** [R36](../req/开发者视角.md)

**规格** 约束有两条：**trace 必须带足够的语义信息使投影可行**；
**筛选与渲染规则属界面层，不得污染 trace 的形状**。

**不做** 为了界面好画而往 trace 里塞展示字段。

**为什么** 分两层的好处在关掉落盘时立刻显现：**事件仍然推给界面，只是不落盘**。
两者不是同一件事。

**验收** `test_trace_carries_readable_labels`

### S112 · trace 默认不落盘，以 run 为单位

**服务** [R36](../req/开发者视角.md)

**规格** 每个 run 一个文件，append-only。默认关闭——关闭时事件仍推给界面。

**为什么** 以 run 为单位是因为**它匹配归因分析的粒度**。

**验收** `test_trace_is_append_only` · `test_files_are_human_readable`

### S113 · 开发者模式是服务级的，启动时选

**服务** [R36](../req/开发者视角.md)

**规格** 在 `.env` 里，启动服务时就定了。**没有运行时开关。**
前端经只读接口得知模式，据此显隐开发者面板。

开发者模式下**强制打开落盘**。

**不做** 做成 session 级；不做运行时切换。

**为什么** 「这台服务是拿来查问题的还是拿来玩的」**不该每个故事各答一遍**。
切来切去会让「这一轮到底记了没有」变成要翻日志才知道的问题。

强制落盘是因为**记了不落盘，下次就查不了了，而查问题总是事后**。

默认关的理由是**体量**：一次往返动辄几万字，一轮四个 agent 上十万。

**验收** `test_developer_mode_records_every_agents_real_exchange` · `test_meta_carries_only_what_is_really_service_wide`

### S114 · 开了就记每个 agent 的完整输入输出，一个都不能少

**服务** [R36](../req/开发者视角.md)

**规格** **四个 agent 加上摘要与归段追问，六个调用点全部记**：
完整消息列表 + 工具面 + 响应原文。

**不做** 只记 director。

**为什么** 此前**后端没有存过任何一份完整提示词**：
装配事件只有条数与字数，响应事件只有工具名；四个 agent 里只有 director 的对话进了
节点、goal_manager 的进了它自己的记录，**writer / state_manager / 摘要 / 归段追问的
输入输出根本不存在**——归段追问连一条事件都没有。

**验收** `test_developer_mode_records_every_agents_real_exchange`

### S115 · 落盘的 trace 要能读回来

**服务** [R37](../req/开发者视角.md)

**规格** 提供按 run 读取的接口。没留过痕的轮次返回**空列表而不是 404**——
那不是错误，只是当时没开。

取数顺序是「**推过来的优先、落盘的兜底**」：当前这一轮内存里就有，更早的去读文件。

**不做** 让开发者面板只看得到当前连接期间的轮次。

**为什么** 事件是推过来的，**刷新一次页面之前那些就没了**。
而开发者模式本来就强制落盘——**记了不给读回来的路等于没记**。

### S116 · 用户的手动编辑也要进 trace

**服务** [R36](../req/开发者视角.md)

**规格** 它是一次状态变更，且**来源是用户**——这两件事都要记下来。

**为什么** 查问题时"这个值怎么变成这样的"必须答得出来，
而"是用户自己改的"是其中一种合法答案。

**验收** `test_a_hand_edit_lands_in_the_trace`

### S117 · 出站消息必须走同一条队列

**服务** —（内部契约）

**规格** 所有出站消息同步入队，由单个发送者顺序送出。**入队是同步的，顺序即产生顺序。**

**不做** 各自开一个任务去发送。

**为什么** trace 事件是从**同步回调**里产生的，各自异步发送就会与生命周期消息乱序
——**界面上会看到「本轮结束」排在「开始新的一轮」前面。**

**验收** `test_trace_carries_readable_labels`

### S118 · 流式是旁路，不是权威

**服务** [R9](../req/推进剧情.md)

**规格** 三条约定：

| | |
|---|---|
| **工具调用不推分片** | `arguments` 是逐字拼出来的 JSON，**半截 JSON 对界面毫无用处**，只会逼前端去猜 |
| **分片可能因断线而丢** | 前端据此显示的东西必须能被最终那份**整个替换掉** |
| **分片必须带来源** | 见下 |

**为什么** 内容分片**两个 agent 都在发**：director 推演途中会写几句自言自语，
writer 写的才是正文。**不按来源分开攒，界面就会把「我先把这一轮推演清楚」当成故事的
第一句**——实跑中攒出 1084 字而节点正文只有 782 字，第一版正是这么错的。

**流不流按 agent 各设一份**（[S159](Prompting.md#s159)）：那份 YAML 顶上的
`stream`。它曾经是一个服务级开关，于是"正文流着看、状态维护不必流"这种差别
根本表达不了——而那正是这个旋钮最常见的用法。

**验收** `test_prose_arrives_in_pieces_while_it_is_written` · `test_the_final_node_is_still_the_authority` · `test_the_agents_after_the_writer_stream_too` · `test_streaming_is_per_agent`
