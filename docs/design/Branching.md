# 分支与回滚

> 树结构与交互**参考常见 AI chat 设计**（编辑/重生成产生兄弟节点，UI 上 `< 2/3 >` 切换，活跃路径是从根到某叶子的一条链）。
>
> 本文档只记录 airp 与普通 AI chat 的**关键差异**：**一个节点的内容包括后台维护的数据。**

## 1. 节点的构成

**一个 run = 一个节点**（D51）。节点内容不止正文：

| 内容 | 产出方 |
|---|---|
| 正文 | writer |
| 细纲 | director |
| 状态增量 | state_manager 写入，run 末随节点原子落盘（D143/D56） |
| 偏离报告 | writer，通常为空（D57） |
| trace 引用 | 见 §5 |

## 2. 核心原则：状态是路径的函数，不是全局单例

普通 AI chat 里节点只有文本，切换分支只需改变渲染的消息列表，上下文就是路径上消息的拼接。

airp 不行：**切换分支必须同时切换后台状态。**

否则会出现最隐蔽也最致命的一类 bug——分支 A 里她知道了真相，切到分支 B 后系统仍认为她知道。**文本看起来是对的，状态悄悄错了**，而这类错误要等很多个 run 之后才以"角色行为不合理"的形式暴露，届时根本查不出源头。

因此：

> **不存在"当前状态"这个全局对象，只存在"沿某条路径重放到某点的状态"。**

实现上可以缓存活跃路径的状态，但概念上必须是路径的函数。细纲历史同理——director 读的细纲历史（[Generation.md](Generation.md) §3）也是路径的函数。

## 3. 这件事是免费的

它不需要任何新机制，是既有决策的推论：

- D19：每 run 必须提交状态增量（哪怕为空）
- D8：trace 完整可回放、append-only

两条合起来，状态**天然就是增量累积的**（event-sourced）。回到任意节点 = 重放该节点之前路径上的全部增量。

这也回头解释了 D19 为什么值得强制：漏交增量不只是让数据与文本分叉，还会**让分支重建出错**——而后者的表现更隐蔽。

**性能**：路径长时逐条重放代价高，用定期快照 + 增量补齐（标准做法）。快照是纯优化，不改变语义。

## 4. 分支操作语义

| 操作 | 树上的效果 |
|---|---|
| 重生成（重 roll） | 当前节点的兄弟节点 |
| 编辑用户输入 | 该用户输入节点的兄弟，其后整条子树不继承 |
| 从中途改方向 | 在指定节点处新建兄弟，原分支保留 |
| 切换分支 | 活跃路径改变，**状态随之重放** |

**任何重生成都产生新节点**，包括"只重跑 writer 不重跑 director"的情形——正文变了，writer 的偏离报告（D57）和 state_manager 据此写下的状态增量都可能跟着变。

其中"只换文风不换走向"是一个**成本优化**：复用 director 已产出的细纲，只重跑 writer。它仍然是兄弟节点，只是生成时跳过了一步。不影响树结构。

## 5. trace 与状态的关键区别

| | 性质 |
|---|---|
| **状态、细纲** | **路径的函数**。切换分支即切换 |
| **trace** | **全局 append-only**，包含所有被放弃的分支 |

trace 不随分支切换而变化，因为 eval 需要看到全部尝试。用户重 roll 五次，trace 里就有五条——**这本身就是 eval 信号**（重 roll 率反映"模型是否在写用户想要的东西"），丢掉等于丢掉最有价值的行为数据之一。

## 6. 开放

- **分支清理策略**：无限保留会膨胀，但 RP 用户可能想长期保留对比线。倾向不自动删除，交用户管理并给出容量提示；不采用"仅保留最近 N 个"的自动淘汰。
- 快照的频率与保留策略。
