# 用户输入的处理

> airp 相对批量写作最本质的差异：批量写作里没有人在环内，内容规格只能由系统自产；airp 里用户持续供给输入，且输入形态与完整度差异极大。

## 1. 不做显式分类

曾以四个例子标注输入的差异：

| 例 | 样例 | 规格度 | 需要补全的量 |
|---|---|---|---|
| 模糊方向 | "往悬疑走""气氛紧张一点" | 最低 | 最大 |
| 目标 | "让他们最终和解""推进到她发现真相" | 低—中：给终点不给过程 | 大 |
| 角色行为 | "我推开门""我说：你到底瞒了我什么" | 中：事件明确，后果未定 | 中 |
| 详细剧情设计 | "她先否认，等他拿出照片再崩溃" | 最高，已接近可执行规格 | 最小 |

**这四个只是举例，不覆盖所有情况，也不应作为分类标签使用。** 不做显式分类的理由：

- 真实输入是混合的——一句话里可能同时含有角色行为、戏外要求和对既有设定的修改。
- 分类是有损的，且失败是**静默**的：归错类不会报错，只会产出"看起来合理但不是要的东西"。
- 即使分类正确，也不直接给出处理方式。分类不是决策。

**保留这些例子的价值**在于它们标出了一个**连续量——输入的规格度**，而不是一组离散类别。见 §4。

## 2. 真正的问题：避免特定失败

设计目标应表述为"避免哪些失败"，而非"如何给输入归类"。已举出三个（**同样是举例，非穷举**）：

| # | 失败 | 描述 |
|---|---|---|
| **P1 漏转述** | 用户给出行为或一段剧情，模型没有转述，直接开始下一段剧情 | 用户提供的内容本该进正文，却被当成了前提悄悄跳过 |
| **P2 覆盖不全** | 模型输出没有完全消化用户指令，剧情只推进了一半 | 用户指令的一部分未被执行 |
| **P3 控制权移交未被识别** | 用户想把剧情控制权交给模型，模型没意识到，不主动推进 | 输入中的"空白"本应被读作授权，却被读作无事发生 |

三者的共同结构：**用户输入与模型输出之间的关系没有被正确建立**——该进正文的没进（P1）、该被执行的没执行（P2）、该被解读为授权的没被解读（P3）。

### P4 用世界规则悄悄换掉用户的动作（D104）

后来由数据化世界补上的第四个失败，它和前三个方向相反：**转述规则要求原样接住用户的动作，而世界规则可能让这个动作不成立。**

实测：用户写「我再来一记御剑斩」，可御剑斩还在冷却，否定项又明写着"不要让冷却中的法术生效"。**两条规则都成立，指向相反。**

规则定为——**动作是锚点，结果归世界**：

- 他确实做了这个动作，不能省略、不能换成别的动作。
- 但结果由世界决定：冷却没过、钱不够、东西用完、伤在牵扯、对方先动了手，都可以让它落空。
- **落空必须写得可见、有据**：写清他试了、以及为什么没成。既不能偷偷换成一个能成的动作，也不能当作他没做过。

模型在实测里选对了，**但设计里从没规定过这件事——它是蒙对的**，而 grader 把它判成了推演错。这类"两条规则都对但打架"的地方，不写下来就等于交给运气。

P2 还引出一项此前遗漏的工作：**校验输出是否完整消费了输入**。它与后台数据一致性校验不同——后者校验内容与账本是否相容，前者校验输入与输出的对应关系。该工作后来被取消，见 D68。

## 3. 控制维度显式化

**这些反例可能互相冲突**，同时满足所有反例的规则未必存在。因此：**把关键控制维度做成用户的显式选择，而不是让模型推断。**

**维度清单已确定，见 [Configuration.md](Configuration.md)**：输入处理（三档）、模型剧情控制权、展开密度、是否允许抢话。文风等不随轮次变的项归 Session 元指令，与控制维度分属两类（D38）。

原先担心的"转述 vs 自主推进"张力在三档定稿后消失——它们被收敛成了一个互斥选择，不存在两个旋钮打架的情形。

### 3.1 已决：显式设置优先于输入内容

显式设置与输入内容本身可能互相矛盾。典型情形：用户把控制权等级调到"模型主导"，但这一轮给出了一整段详细剧情——等级说放手，输入说别动。高规格度的输入本身就是低控制权移交的信号，与旋钮位置无关。

两个候选：

- **显式优先**：尊重设置，即使输入看起来相反。可预测。
- **内容优先**：从输入推断真实意图，覆盖设置。符合直觉，但把推断请了回来——而推断正是 §1 要避免的。

**已决：显式优先**（[Decisions.md](../Decisions.md) D15），乐观假设用户尊重自己的显式设置。

需要诚实记录的残留成本：显式化并没有消除推断，只是把推断从"这句话属于哪一类"缩小成了"设置与输入冲突时谁赢"。选择显式优先等于把这个残留问题也一并消除，代价是可能出现"我明明写了详细剧情它却全改了"这类体验。

### 3.2 粒度与代价（已决）

**显式化的代价边界不在维度数量上，在单轮覆盖的交互形态上**（D45）。绝大多数设定设一次长期有效；单轮覆盖做成快捷方式（`/只转述`）而非选择题，交互成本差一个数量级。分层见 [Configuration.md](Configuration.md) §5。

## 4. 规格度决定补全工作量

即 director 的职责：**把输入补全成无文风约束的文章（细纲）**。这项工作必然存在，但**工作量随输入规格度递减，且可以为零**。

- 输入已足够具体时（如上表第四例），补全工作量应为零。再走一遍是把它压缩再解压，纯损失。
- 输入只给方向时，补全工作量最大，且往往需要先向用户澄清。

**长循环自主创作**是这条的极限情形：完全没有用户输入，细纲必须自产。这是补全工作唯一不可替代的场景。

注意这是关于**工作量**的连续陈述，不需要先分类就能成立——这正是 §1 说分类不必要的原因之一。

此前曾表述为"与用户介入**频率**成反比"，需修正：变量是规格度而非频率。

## 5. 元操作与内容输入的分离

元操作（回滚、分支、停止、改设定）与内容输入不同：它们进控制面，不进模型上下文。这一条独立成立。

此前还曾主张把内容输入进一步分成"戏内"与"戏外引导"两条通道。**已取消**（[Decisions.md](../Decisions.md) D16）：它等价于「输入处理」维度的三档划分，既已做成显式控制，就不需要额外再设一层通道。

## 6. 与流式的关系

已决：**流式让步于 agent 设计**（[Decisions.md](../Decisions.md) D7）。后果：

- 校验可以在提交前拦截，不需要"滞后一拍的检测"这类为保住逐 token 流式而引入的复杂设计。
- 但每个 run 的用户可感延迟 = 整条工作链的串行时间。这与 token 成本是两个独立的预算。
- 长循环模式下此问题较轻（用户在观看连续产出，不在等某一次回复），密集交互模式下最重。与 §4 指向同一方向：**输入规格度越高，可省略的工作越多，延迟越低**。
