# state

> 三种数据的区分见 [../Glossary.md](../Glossary.md)；检索方案见 [Retrieval.md](Retrieval.md)；谁读谁写见 [Architecture.md](Architecture.md)。
>
> 一句话：**有限建模、结构化存储、模型判断、代码只管契约。**

## 1. 为什么只有它是必做的

长程一致性解决的是**上下文窗口的物理限制**——再强的模型也无法在几百个 run 之后记住早期细节。这个约束不随模型能力提升而消失，因此这块工作的收益不会被更好的模型吃掉。

对照之下，多 agent 角色化与规则化解决的是**模型推理能力不足**，收益随模型能力递减（见 [Optional.md](Optional.md)）。这条判别式是"必做 vs optional"的分界线（D12）。

## 2. 建模：不预设任何维度

**这是本文档最重要的一条，而且是推翻重来的结果。**

曾按「在场 / 时间 / 地点 / 谁知道什么」定义过一层固定核心 schema。该设计已整层作废（D74）——错误不在字段选得不好，而在**这类 schema 在原理上就定不下来**：

- **时间是服务于写作的。** "下午一点""是晚上""过了一个月"在不同情境下影响完全不同，粒度与形态都不定。加字段解决不了——那只是把猜测挪到更深一层。
- **地点同样。** 可以是某国家、某城市、某酒店、"婚礼进行中"、"山顶"。
- **知情不是每个故事都要维护。** 而角色能挂的属性——性格、能力、与他人的关系——也不可能预先穷举。

真正的问题是：**我在猜哪些维度重要，而这取决于故事。**

两条出路——**由 session 级声明**（显式，符合 D15）或**由模型动态决定**——对存储层的要求是**一致的：给足自由度**。因此存储层不预设任何维度，只提供命名空间与读写语义；"哪些维度存在"往上挪一层（这个问题**没有解决，只是移位**，见 Q27）。

### 落地形态

键是自由字符串，`.` 分隔表达从属但**仅用于渲染分组**，系统不赋予它语义。写入语义有三种：`set`（覆盖，`null` 删除）、`append`（追加去重）、`remove`（从清单拿掉，见下）。

```
时间          "第三日 傍晚"
时间.距上轮    "三小时后"
地点          "康德酒店 302 房"
林.在场        true
林.性格        "谨慎，话少"
林.知情        ["照片的存在"]
```

**"离场再出场"因此天然成立**：只改提到的键，其余保持原状——不需要"角色实体"这类预设。

#### `remove`：`append` 缺失的逆运算（D96）

原先只有增没有减，清单就只增不减。要去掉一项只能 `set` 整个列表——而整体重写既贵又容易丢项。实测模型干脆绕开了结构：

```
初始   "沈砚.随身": ["青锋剑", "止血符 ×2", "定身符 ×1"]     ← 清单
写回   "沈砚.随身": "青锋剑、止血符 ×4、定身符 ×1"            ← 字符串
```

**清单被拍平，此后再也无法单独增删其中一项，且不可逆。**

根因有两层，光修提示词不够：

1. **缺语义** —— 没有 `remove`，"用掉一张符"无法表达。
2. **渲染丢形状** —— 清单原先渲染成 `随身：青锋剑、止血符 ×2`，**和一个字符串长得一模一样**。模型看不出这是清单，写回字符串是合理反应。现在渲染成 `随身：清单：青锋剑、止血符 ×2`，形状可见，同时也告诉模型这里可以 append / remove。

`apply` 的顺序是 **set → remove → append**，因此"换掉一项"能在一次写入内表达：`remove` 旧计数 + `append` 新计数。修好后模型自己用出了这个模式。

**这个缺口在纯文学场景里永远看不见**——那里的清单（知情、经历过的事）天然只增不减。数据化的世界才会暴露它：消耗品会用完，随从会离队，伏笔会被揭开。这是一条方法论：**判据和语义都要拿一个反向的世界压一遍**。

这不违反 D20（不让模型自由定义 schema）：模型做的仍是"记一个键值对"（数据层），不是"设计一个数据结构"（元层）。schema 因此从三层塌成两层：**自由 KV（即全部）+ 模板库（session 级声明，尚未做）**。

### 定位：state 是 history 的捷径（D99）

**信息本体在 history 里。state 不是第二份记录，是一条捷径**——把每轮都要用、又不该每次回头翻的那几条拎到眼前。

这条定位撑起下面全部判据，也带来三个推论：

1. **判据是双条件的**（见下），两条各排掉一类错记。
2. **删键不等于丢信息**——那件事仍在 history 里。因此 state 该保持短，`set null` 也才成为一个模型敢用的动作。
3. **结构化靠鼓励，不靠强制**——既然是速查表，形状比文采重要。

它还修正了 D64 的一半：细纲里写了但没进 state 的，**可以从 history 回捞**；只有那些只存在于正文里的事实才真正不可自愈（director 不读正文）。

### 判据：记什么，不记什么（D95 / D99）

存储层不预设维度，"该记什么"就完全落在提示词上，判据必须说准。

**先过一道门槛：需要随时看见它，不值得为它去翻前情。** 这一轮的气氛、谁站在柜台哪一侧——前情里本来就有，抄进来只是占地方。

过了门槛之后，**该记的有两类，"忘了的后果"完全不同**（D109）：

| | 忘了会怎样 | 例子 |
|---|---|---|
| **约束类** | 写出**不可能发生**的事 | 谁死了、谁不在场、谁不知道什么、受了什么伤、还剩几块钱、法术还在冷却 |
| **悬置类** | 不出错，但**烂尾** | 掏出来搁在桌上的枪、许下的承诺、没被回答的问题、没拆的信、撂下的"我还会回来" |

**悬置类最容易漏，恰恰因为它什么也不禁止。** 枪挂在墙上，不写它照样写得下去——单靠"会不会出逻辑错误"这条判据，它必然被丢掉。这是原判据的缺口，不是模型的失误。

判据要够窄，否则布景会被整批当成伏笔记进来：

> **有人特意让它出现，而它还没有下文。**
> 桌上的杯子不记；被人拿起来又放下的那个杯子才可能要记。

**兑现之后立刻删。** 枪响了、答复给了、信拆了，那个键就完成了任务。于是 state 里的悬置项恒等于**当前还欠着的账**——一份会自己清空的待办，不是只增不减的清单。

这一条还有个连带作用：**它把一部分伏笔从检索问题变成了记账问题。** 有意埋的伏笔进 state；只有"当时无人在意、后来才被挑出来变成关键"的细节，才真正需要翻原文（[Retrieval.md](Retrieval.md)）。

两类之外的门槛，恰好各挡住一类实测出现过的错记：

| 错记 | 挡它的是 |
|---|---|
| `照片.朝向: "正面朝上"` | 两类都不是——它什么也不约束，也没人特意让它出现 |
| `现场.本轮: "林昭进店，陈屿从里屋出来……"` | 门槛——前情里就是它，抄一遍没有意义 |

曾用过的判据是**时态**的——"记的是下一轮开始时世界是什么样，不是这一轮发生了什么"。它排得掉情节复述，**但排不掉记得过细**：`照片.朝向` 完美通过时态测试，它确实是下一轮世界的样子。缺的是**用处**这一维。

**存续时长不是判据。** 这一条是被数据化世界纠正的：

| | 存续 | 该记吗 |
|---|---|---|
| `沈砚.冷却: 御剑斩还剩 2 回合` | 两轮 | **必须**——漏了就会重复放技能 |
| `照片.朝向: 正面朝上` | 永远 | 不必——写岔了没人算得出矛盾 |

因此"只在这一两轮内有意义的就不记"这条经验是错的，它会把资源与冷却一起误杀。

**真正好用的自检是「下一轮开始时，这条还成立吗」。** 写入冗余在两个场景里都是占比最高的一类（各 40%），而且证据高度一致——模型把**这一秒的画面**当成了状态：

| 实测写出的键 | 下一轮还成立吗 |
|---|---|
| `青鬃狼.状态: "侧扑已至近前，即将落身"` | 否 |
| `照片.状态: "柜台，正面朝上"` | 名义上成立，但没人会去看 |
| `青鬃狼.第二头: "回应嚎叫后未现身"` | 否，且它记的是"未明" |

判据里早就点名禁过物件朝向这类，**说明光加禁令没用**。换成一个每轮必过的自检更有效：画面归正文，state 只留画面**留下的东西**——他受了伤、她把照片给出去了、那件事被说破了。

复跑确认这一类**整类消失**了。

### 键名漂移：提示词拦不住的那一半

同一次复跑暴露了另一件事：`沈砚.冷却` 已经存在，模型却另起了一个**裸键** `冷却`。那一轮 state 里两个冷却键并存、值还不一样；它下一轮自己发现并 `set null` 删掉了，**但中间那一轮是脏的**。

提示词里已经写着"新建键之前先看上面有没有已经在说同一件事的键"，没拦住。因此这一条改由 program 采样器兜（[Optimization.md](../Optimization.md) §3 的"只看形状不看内容"）：

> **只报「一个裸键 vs 一个带前缀的同名键」。**

判别式必须这么窄——`林昭.知情` 与 `陈屿.知情` 共享词尾却都是对的，**两边都带前缀就不是歧义**，那正是 `.` 分组要表达的东西。误报这种会让标记立刻失去价值。

至于 `位置` 与 `地点` 这类**近义但不同词**的漂移，代码判不了，仍然只能靠把已有键列表回给模型（D75 的已知代价）。

### 鼓励结构化，但不强制 schema（D99）

不预设 schema（D20/D74）**不等于放任写成散文**。既然 state 是速查表，形状比文采重要——这件事只能靠提示词鼓励，代码这一侧最多报告形状（见 §4）。

提示词里给的都是可照做的具体指令，不是"请保持结构化"这类空话：

| 鼓励 | 反例（都来自实测） |
|---|---|
| 能用数字就别用句子 | `"身上还剩一块灵石"` → `沈砚.灵石: 1` |
| 能用是/否就别用描述 | `陈屿.在场: true` |
| 一类东西归进一个清单 | `沈砚.随身`、`林昭.知情` |
| 一个键只装一件事 | `许平: "已故男子，照片中的另一人；名字由陈屿说出；与陈屿相识；两人关系与死因未明"`——裸实体名做键，没有维度，于是变成杂物堆，以后谁也改不动 |
| 同类的事用同一套键名 | 别一个人叫 `沈砚.灵石`、另一个叫 `孙执事.身上的钱` |
| 值的形状保持不变 | `3` 不要写成 `"3"`；清单不要拍成一句话（D96） |

另外两条否定：

- **不记「未明」「不确定」。** 没记的东西本来就是未知的，写出来只占地方。
- **不记来源。** "名字由陈屿说出"属于 `某人.知情`，不属于被说的那个东西。

state 只增不减会把真正重要的几条淹掉，所以不再约束后续的键要 `set null` 删掉——**删了不算丢东西，那件事仍在 history 里**，这一句是模型敢删的前提。

### 初始状态：一切分支共同的重放起点

**一份 worldbook 可以开出好几个 session**（D170），它的内容分两路落地：`world` /
`character` 条目的正文进 worldinfo（静态），`state` 条目的 `values` 进初始 state
（后续由剧情推进）。

之所以要分成两类条目，是因为**一条设定本身是混的**。角色卡里，性格、说话习惯、
背景经历是**静态的**（不因剧情改变）；而他现在在哪、和谁什么关系、知道什么，
是**会变的**。

没有机制表达后者时，模型只能把它从设定里**抄**进 state——实测两次都这么做了。
而副本会在设定被改动后与之分叉，正是 D61 那条划分要防的事。

```
WorldbookEntry(name="林昭", kind=CHARACTER,        # 静态 → worldinfo
               content="三十岁出头，本地报社记者。做事谨慎。",
               voice="话少，先观察再开口")          # 语言习惯，只进 writer
WorldbookEntry(name="林昭·初始状态", kind=STATE,    # 会变 → 初始 state
               values={"林昭": {"在场": True, "知情": [...]}})
```

**关键不在于它让模型能做什么，而在于它让模型不必做什么**：这些键一开始就在默认包
里，模型看得见，自然只会去**改**它。**移除诱因比在提示词里禁止可靠**——这也正是
P10 的精神。

（早先这两样挤在同一条条目的 `content` 与 `seeds` 上，共用一个可展开开关。拆开
是因为可见性天然不同步：角色背景几百字、该按需展开，而「他在不在场」必须每轮都
在眼前，D158。「种子」这个叫法也一并废了——它暗示"发芽之后就与它无关"，而语义
恰恰相反。）

实测的附带收获：这些键成了**命名锚点**。有它们之前模型自造 `时间: "白天"`；有了之后它直接改既有的 `时间` 键。这压住了 D75 说的键名漂移，比"请复用已有键名"这句提示有效得多。

### 共享一份设定，跑着的故事会不会被改坏

**答案不需要新机制，就在这两样东西各自什么时候被读**（D170）：

| | 什么时候读 | 所以改它 |
|---|---|---|
| 初始状态 | **只在第 0 轮之前**——第一轮开始时冻结进 `Session.initial_state` | 只对还没开始的故事有效 |
| 静态设定 | **每轮现读** | 直接影响所有故事的下一轮 |

后者是对的：那是「这个世界是什么」，改它等于改角色卡。前者也是对的：第五轮写着
「她掏出钥匙」而钥匙来自初始状态，把它删掉，那一轮就凭空多了一把不存在的钥匙，
且没有任何地方会报错（D158）。

### 已作废的两轮修补，记录在此以免重走

固定核心那一版曾被这样修补过，**这些修补同样作废**——问题不在字段，在这层 schema 本身：

- ~~知情建成"角色 × 事件"的关系矩阵~~ → 它隐含要求一个**事件实体**，而系统里没有、也不打算加。
- ~~角色档案与在场状态分离成两个概念~~ → 原因是全量替换的名单会让离场角色的知情一起丢。自由键天然没这个问题。
- ~~时间分绝对与相对两个字段~~ → 分开本身是对的观察，但它仍然是在预设"时间该长什么样"。

## 3. 注入：与 history / worldinfo 同一个模式

**全量键名 + 体量小的值内联，大的只给体量**（D77），由模型按需 `state_query` 展开。

**值的形状必须在渲染里可见。** 清单原先渲染成裸的顿号串，和一个字符串没有区别，模型据此写回就把它拍平了（D96）。现在清单标出 `清单：`，空清单标 `（清单，空）`——这同时告诉模型这里可以 `append` / `remove`。这是"注入格式会反过来决定写入质量"的一个实例：**模型只能写回它看得出形状的东西。**

这和 history、worldinfo 是**同一个模式**（D63），因此同样满足 [Retrieval.md](Retrieval.md) 的准入标准：规则只调精度、不做相关性筛选，模型始终知道有哪些键存在。

这不是刻意统一的结果，是取消固定核心之后自己塌下来的——原先"核心带值 / 自由槽位带键名"的区分本身就是那层猜测的产物。

**连带好处**：结构化后的核心状态极小，可以**无条件随每个 run 带入 director 的上下文**，不需要判断"这一幕需不需要"。对比 lorebook 必须命中才有、命中多了又撑爆。

## 4. 代码能做什么

### ~~契约完整性~~ —— **这一类也没了**（D143）

> 曾经的 E0：**校验"有没有提交状态更新"，而不是校验"更新的内容对不对"。**
> 每个 run 必须提交状态增量，哪怕是空的（D19）——强制那一次空调用是为了
> **区分「确实没变化」与「模型忘了提交」**。

**它随 D143 自然作废。** 那条契约管的是 director：它边推演边写状态，所以需要一个
"你写过了吗"的检查。状态维护后置到 state_manager 之后，那一步**就是它的全部工作**——
它跑完这一轮必然有一个增量（可能是空的），没有"忘了提交"这种失败模式可言。

于是代码这一侧**一类检查都不剩**：内容判断全交给模型，程序只做采样标记（§4 下节），
而标记从不影响运行时行为（D43/D44）。`TraceEventType.CONTRACT_CHECK` 也一并删了——
留一个谁都发不出来的事件类型，等于让 schema 承诺一件代码不做的事。

### 结构性交叉比对 —— 不做

原本设想比对模型自己产出的不同部分是否自洽。**落地时确认这一类在本项目里不成立，已取消**（D29 修正）。

| 设想的检查 | 为何做不了 |
|---|---|
| 时间单调 | 时间是自然语言（"傍晚""第二天"），无法机械比较 |
| 说话者 ⊆ 在场 | 从正文抽出说话者是语义工作，代码做不了 |
| 地点可达 | 需要地点拓扑图，而地点只是个字符串 |
| 知情者 ⊆ 在场 | 看似成立，实则不可靠——信息可经转述、书信、监听获得，**不在场并不蕴含不知情** |

**硬做只会得到假警报，而假警报比不检查更糟——它会让人不再信任系统。**

其余落到 **eval 采样标记**（"正文很长但增量为空"、"正文明显短于当前展开密度"）：那不是判断器，是采样器（D43），从不影响运行时行为。

### 一个必须避免的错觉

若把 `关系[A][B] = 决裂` 存成结构化字段，代码去读它、比对它，看上去像"代码判定"——**但该字段的值本就是模型写进去的**。语义判断发生在**写入时**，代码检查发生在**读取时**；后者不是独立验证器，只是一次查表（D30）。

这个诱惑很强，我在 goal 判定上犯过一次同样的错。

## 5. 写入侧：乐观处理，靠用户兜底

写入与检索的**风险不对称**：

- **检索遗漏可自愈**——这次没查到，下次还能查。
- **提取遗漏不可自愈**——这一 run 漏记了"她知道了真相"，之后永久丢失，因为 **director 不读正文**，没有任何机制能回捞。

D19 只解决"有没有提交"，解决不了"提交得全不全"，而后者代码查不出来。

**结论：不用系统机制解决，改为乐观处理 + 让用户参与维护**（D64）。

> **state 必须是用户可随时查看 / 编辑的**（D65）。

这不只是兜底，**state 可见本身就是产品价值**：用户看到"她知道真相：是"这一行，既能纠错，也能理解当前剧情状态。现有工具完全没有这一层。

编辑语义：**直接改写节点数据，不做依赖检查**——乐观假设用户只改最新输出，此时本无下游。曾提议"插入一个只含 delta 的新节点"以保护不可变性，已否决：为一个乐观假设下不存在的问题增加复杂度，也不符合常见 AI chat 的编辑语义。

## 6. 参考：TauriTavern 没有做这件事

作为**反面数据点**记录。它的 workspace 是**文件系统，不是事实模型**：三类资源（materialized / virtual / generated），目录 `input/ output/ plan/ scratch/ summaries/ persist/`，全为文本文件。18 个内置工具中**没有任何** entity / timeline / relationship 查询，没有事实表，没有一致性检查器。一致性依赖模型自行在 `scratch/`、`summaries/` 里维护自然语言笔记，无强制、无校验、无结构。

注意其文档中的 "consistency" 指的是**文件系统层面**的（sha256 快照、commit 前建 checkpoint、run 内回滚只恢复 workspace），与"故事内容不矛盾"是两回事。

其世界信息即 SillyTavern 的 lorebook。**lorebook 的结构性缺口**：关键词漏命中则该出现的设定不出现；命中过多则撑爆上下文；条目互相矛盾无任何机制可发现。但最关键的是——**它表达静态设定（她是谁），表达不了动态状态（她现在在哪、知道什么、刚和谁吵过架）**。而 RP 中的出戏绝大多数来自动态状态。补上这一层正是创新点 (a) 的落点。

**结论：workspace-as-filesystem 这条路走到底，就是模型自己写 markdown 笔记。**
