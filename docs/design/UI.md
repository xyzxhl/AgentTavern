# 界面

> 界面是 trace 与节点树的**投影**（D25）。这份文档回答：投影哪些、摆在哪、为什么。
>
> 对应 Decisions.md D25 / D45 / D46 / D65 / D112 / D147 / D156 / D170 / D171。
> 技术选型见 [../TechStack.md](../TechStack.md)，这里只谈形态。

## 1. 出发点：界面缺的不是零散功能，是「回头」这一整个方向

第一版界面覆盖的是一条线：**输入 → 看正文 → 再输入**。而系统本身是一棵
**可回头、可改写、可调参**的树：

- D46/D147 —— 重新生成产生兄弟节点，`< 2/3 >` 切换回去
- D65 —— 用户可以直接改细纲、正文、状态
- D112 —— 用户随时可以自己断段
- D45 —— 单轮覆盖控制维度

这四条决策的后端**全部完成且有测试**，而界面上**一个入口都没有**。逐条：

| 能力 | 后端 | 界面 |
|---|---|---|
| 重新生成 | `regenerate` 消息 | ~~无~~ → 每一轮的 `↻`（批 2） |
| 分支切换 | `switch_branch` + `GET …/siblings` + `branches` 推送 | ~~无（store 里 `case "branches": break;`）~~ → `⟨2/3⟩`（批 2；兄弟关系改随路径给，见 D177） |
| 编辑节点 | `edit_node` + `PATCH …/nodes/{id}` + `USER_EDIT` trace | ~~无~~ → 每一轮的 `✎`，细纲 / 正文 / 状态（批 2） |
| 手动归段 | `POST …/close-segment` | ~~无，`api.ts` 里连方法都没有~~ → 每一轮末尾的「⌄ 在这里断段」（批 4） |
| ~~单轮覆盖~~ | ~~`Submit.control_override`~~ | 已被 D174 取消——取值上调之后没有被覆盖的对象了 |

**`switch_branch` 缺失的后果最重**：D147 的设计是「创建受限、切换不受限」——
分支只能在当前节点上开，想在更早处分叉要先切过去。切换是那条路唯一的入口，
没有它，重生成产生的兄弟节点**永远回不去**。

这是同一个失败模式的第五次（前四次：`MODEL_REQUEST`、`model_authority`、
`RunStarted`、`USER_EDIT` —— 都是定义齐全、单测覆盖机制、而**接线没做**）。
前四次是一个事件，这次是四条决策的功能量。**记在这里当作判据**：一条决策落地
与否，看的是它**从用户那一侧够不够得着**，不是模型和测试跑不跑得通。

### 另外三类缺口

**只读的：** `StatePanel` 只能看。D65 的原话是 state 必须**用户可查看/编辑**。

**没有接口的：** 提示词。D135/D136 把顺序和正文搬进 YAML，理由原话是
「调位置 = 移动一行，加一节 = 插一行，都不用碰 Python」，但**没有任何读写接口**——
现在只能去编辑器里开文件，而提示词是这个项目里改得最频繁的东西。

**攒了不显示的：** `usage`（store 每轮在累加 token，界面一个字都没有）、
`notes`（`RunFinished` 带着 eval 采样标记，store 直接丢掉）、`Branches`。
**三样都补上了**（批 2 / 批 4）：token 在头部、采样标记在每一轮末尾、
兄弟关系改成随路径一起给（D177）。

## 2. 一条判据：一件事一个入口

这是 D171 删掉 `character_voices` 的那条理由，**它同样管界面**：

> 同一件事有两个入口，两个入口迟早对不上；而对不上的时候不报错，
> 只是其中一个悄悄显示了旧的东西。

第一版违反它的地方是**「本局设定」**：从故事里点它能编辑 worldbook，从设定库
点也能，两个页面各自维护自己的列表状态。取消掉——故事那边只留一个**指向**
设定的标签，编辑永远在设定页发生。

同一条判据推出下面几处：状态编辑不做成两个概念（见 §5）、导入不做成两套流程
（见 §4）。

## 3. 布局

```
┌──────────────┬─────────────────────────────────┬────────┐
│ 提示词管理    │ 雨夜  deepseek-v4-flash          │ 状态   │
│ 世界书管理    │ 〔旧城区 ↗〕      12.4k tok      │ 目标   │
│──────────────│ 配置  开发者                     │        │
│ 会话      +  ├─────────────────────────────────┤ {…}    │
│ ● 雨夜       │ › 我推开门          ⟨2/3⟩ ↻ ✎    │        │
│   旧城区     │ ▸ 推演 8 步                      │        │
│   第二局     │ 正文……                           │        │
│   旧城区     │ ▸ 写完之后 4 步          1.2k tok │        │
│   修真记     │ ───── 第一段结束（3 轮）─────     │        │
│   修真界     ├─────────────────────────────────┤        │
│              │ 目标推进中  3/∞          暂停    │        │
│              │ [输入框]                     ➤   │        │
└──────────────┴─────────────────────────────────┴────────┘
```

**左栏分两段**：上面是**独立页面的入口**（点了主区整个换掉），下面是**会话记录**。

不做成 tab 切换。tab 会让「会话列表」在看设定时消失，而那没道理——设定和故事
不是互斥的两个模式，前者是后者的材料。入口在上、列表在下，两者同时在场。

**主区**默认是正文流；点上面任一入口，整个换成那个页面（不是浮层，见 §4）。

**右栏**只在正文流下出现（状态 / 目标）。独立页面要宽。

**浮层只剩一个**：开发者面板。它的语义确实是「临时打断，看完就关」。
「配置」那个浮层没了——控制维度与开关去了 agent 管理，题材与尺度是 worldbook
条目，标题在会话列表上就地改，剩下的字体与色彩去了全局设置（D178）。

## 4. 世界书管理

worldbook 是一级资产（D170），所以它是一个**页面**，不是浮层。浮层的语义是
临时打断，而编辑设定是要待很久的事。

```
┌──────────────┬──────────────────────────────────────────┐
│ 提示词管理    │ 旧城区                        导出  导入 │
│[世界书管理]   ├──────────────────────────────────────────┤
│──────────────│ 名字  [旧城区              ]              │
│ 导入  + 新建 │ 题材  [现代，悬疑，克制      ]              │
│ ● 旧城区     │ 尺度  [                    ]              │
│   3 条 · 2 局├───────────────────┬──────────────────────┤
│   修真界     │ 世界  旧货店       │ 正文……                │
│   8 条 · 1 局│ 角色  陈屿         │                      │
│              │ 角色  林昭 ★用户   │ 语言习惯……            │
│              │ 状态  起点         │                      │
└──────────────┴───────────────────┴──────────────────────┘
```

**「几局故事在用」必须显示。** 改设定对它们全都生效，删之前更得看得见——
被三局故事用着的设定被删掉，那三局会当场失忆。服务端也拦（409）。

**整份设定的属性要能改。** 名字、题材、尺度现在只有后端接口，前端只有一个
`prompt()` 改名字。它们和条目列表在同一页，一个正经表单。

### 导入分两层，缺的是外面那层

| 位置 | 动作 | 第一版 |
|---|---|---|
| 栏顶「导入」 | 导入文件 → **得到一份新设定** | **没有** |
| 某份设定内「导入」 | 往这一份里追加 / 替换 | 有 |
| 某份设定内「导出」 | 导出这一份 | 有 |

缺的那条恰恰是最常用的：拿到别人分享的设定文件时，你要的是「变成我的一份新
设定」，而不是「先建个空的再往里导」。需要后端新增 `POST /worldbooks/import`。

### 新建故事要选设定

第一版的 `+` 直接建一份空 worldbook，于是每开一局就多一份孤儿设定。改成先选：
用哪份已有的，或新建空的。设定页那边保留「在这上面开新故事」——那是
「先有世界，再有故事」那条路。两条路都要留：要求先建设定才能开会话，等于在
最没有想法的那一刻逼人做决定。

## 5. 一轮的完整形态

操作**悬停才出现**，不常驻——读正文的时候它们全是噪音。

```
› 我推开门                              ⟨ 2 / 3 ⟩   ↻ 重生成   ✎ 编辑
▸ 推演 8 步
正文……
▸ 写完之后 4 步                                            1.2k tok
────────────── 第一段结束（3 轮）──────────────      ← 已归段的显示
                  ⌄ 在这里断段                       ← 悬停时出现
```

- `⟨ 2/3 ⟩` —— D46 那个切换器。**它是回到历史分叉点的唯一路径**（D147）。
- `↻` —— `regenerate`，在当前节点的父下开兄弟。
- `✎` —— 展开成节点编辑器：**细纲 / 正文 / 状态**三样在同一处，因为它们是同一个
  节点的三个面。改完会在 trace 里留一条 `USER_EDIT`（D50：手改过的正文不能在
  回看时被当成模型的产出）。
- `⌄ 在这里断段` —— D112 的第三条支路。自动追问判早了或判晚了，用户随时可以自己断。

### 状态：两个操作，都作用在**当轮的增量**上

一轮的产出里，状态那部分是**一串修改指令**（`state_delta`）。用户能碰的是两样：

| 操作 | 你操作的对象 | 系统怎么落 |
|---|---|---|
| **改指令** | 那一轮的 `set` / `append` / `remove` | 直接改增量——它就是权威数据 |
| **改结果** | 那一轮**之后**的状态树 | 和这一轮之前的状态求差，反推成增量写回去 |

两者都**只改这一轮**，下游照常重放。那不是危险，那就是 event-sourced 的正常
行为（D48/D49）——**不要把它描述成「改历史会连锁」**，那会让用户不敢用一个
本来正常的功能。

界面上不需要两个概念，只需要同一个编辑器的两个视图：

```
第 3 轮的状态                         [指令]  结果
  set     林昭.知情   ["照片的存在"]
  append  沈砚.随身   ["止血符"]
  remove  沈砚.灵石

第 3 轮的状态                          指令  [结果]
  { "林昭": { "在场": true, "知情": [...] },
    "沈砚": { "随身": [...] } }
```

侧栏「状态」面板的编辑按钮 = 对**最新一轮**做这件事（日常说的"改现在的状态"）；
历史某一轮走它自己的 `✎`。**同一个操作，两个入口，不是两个概念。**

### 输入框旁：没有单轮覆盖

D45 曾要求把单轮覆盖做成快捷方式（`/只转述`）。**那条已被推翻**（§6）：控制维度
的取值上调到提示词层之后，"覆盖"没有被覆盖的对象了。输入框旁边什么都不加。

## 6. agent 管理（提示词与工具）

### 判据：所有被输入模型的内容，用户都能审查和修改

这一条比"提示词可编辑"强得多，它同时管**工具描述**、**追问**、以及渲染里嵌的
那些短句。它也解释了为什么装配器要**做减法**：审查的前提是**所见即所得**——
编辑器里显示的那段文字，必须就是模型收到的那段文字。装配器每替用户多做一件事
（自动包标签、前后垫话），编辑器和模型看到的就差一点。

### 提示词只有三类

| 类型 | 用户能改什么 | 内容从哪来 |
|---|---|---|
| **text** | 正文 | 用户写的字，可含 `{{var}}` 单值占位 |
| **context** | **只有位置** | 代码整段生成——世界设定、当前状态、前情、本轮细纲、正文上文 |
| **choice** | 每一档的正文 **+ 当前选哪一档** | 用户写的字 |

三类**统一可上下拖动排序**。`context` 是纯占位：它的内容是数据，不是提示词。

`{{var}}` 与 `context` 的分界是**体量与位置**：前者是嵌在句子里的单值
（`本次目标：{{goal}}`、`用户扮演：{{user_character}}`），后者是独占一条消息的
一大块。两个都要，不能合并。

D175 之后 `{{var}}` 只剩这两个用户——题材与尺度都变成 worldbook 条目、跟着
`worldinfo` 那一大块走了。**类型仍然要留**：剩下这两个恰好是"必须嵌在句子里"的
典型（光给一个名字没有意义，得说"用户扮演的是他"）。

### 装配器要移除的东西

| 移除 | 为什么 | 替代 |
|---|---|---|
| `title` 自动包 `<标题>…</标题>` | 编辑器里看不到那对标签，而模型看得到——违反所见即所得 | 要标签就自己写进 `text` |
| `intro` / `outro` | 同上。它们存在的理由是「`context` / `choice` 的正文由代码生成，YAML 那侧一个字也写不进去」 | **在它前面 / 后面放一条 `text`**——有了拖动排序，这比两个特殊字段直接 |
| `key`（引用顶层命名块） | 它的理由是「长文本留在原处更好编辑」，**有了编辑界面这条就不成立了** | 正文内联进 section，YAML 变扁 |

**取消自动标签有一个要盯的风险**：每个 section 本来就是一条独立消息，消息边界
即是边界，所以标签在理论上是冗余的——但**部分供应商会把连续的同 role 消息合并**，
合并之后边界就没了。真出问题时的补法是**让用户自己在 `text` 里写标签**（那时它
可见、可编），**不是把自动包裹加回来**。

### `choice` 的当前选择上调到提示词层

文风、视角、转述与推进、铺陈程度、抢话——这几档的**当前取值**从 session 搬到
提示词文件里，不再绑定 session 或 worldbook。一处定义、一处取值、一处修改。

**连带作废**：`SessionPatch.control`、设置面板里的"控制维度"整块、
`/meta` 的 `options`（前端不必再现读档位，档位就在这一页上）。

**单轮覆盖一并去掉，这推翻 D45。** 既然取值只有一处，"覆盖"就没有被覆盖的对象了；
`ControlOverride`、`Submit.control_override`、`ControlDimensions.merged_with` 全部删除。
D45 原本的理由是「显式化的代价边界在交互形态上，不在维度数量上」——那说的是
*怎么呈现*一个存在的维度，而现在维度本身搬走了，那条理由够不着新的形态。

**已知代价**：同一台服务上的两局故事不能再有不同文风、不同尺度。这是"层级上调"
的定义本身带来的，不是实现取舍。

### 工具描述也归这里 —— 这推翻 D140 ①

D140 当时判「工具描述不搬进 YAML」，理由是「一个工具怎么描述自己，跟它的参数、
错误信息、注册条件是同一件事，拆开写两处必然对不上」。**上面那条判据压过它**：
描述是模型读到的字，就必须可审查可修改。

但 D140 担心的漂移是真的，所以：**参数 schema 仍由 Python 生成，在页面上与描述
并排显示，只读**。漂移因此摆在人眼前，而不是藏在两个文件里。

`ask_question` 的描述按 `model_authority` 分三档（D140②/D155）——它天然就是一个
`choice`，三类不必为工具再加第四类。

### director 有三个附属提示词

它们不在 director 的消息序列里，是**运行时另外追加的整条消息**，所以在左栏里
作为 director 的子项：

| | 现在住在哪 | 说明 |
|---|---|---|
| **追加输入** | `director_append.yaml`（片段文件） | 引导 / 打断插进来的那一条（D145②） |
| **空回催促** | `director.yaml` 的 `nudge` 选项组 | 模型只回文本没调工具时推它一句 |
| **归段追问** | **`postrun.py` 里的 Python 字符串** | 生成后问它这一段收了没有（D112）。**它现在完全够不着** |

第三条是这次审计新发现的：`_CLOSE_SEGMENT` 是一段四百多字的、模型每轮都会读到的
提示词，而它硬编码在 Python 里。

### 渲染文案也是「特殊」，同样分到 agent 名下

严格按判据，模型读到的**还有一批嵌在渲染里的短句**，它们既不是 section 也不是
工具描述：

```
用 worldinfo_read 按 ref 展开。          ← render_worldinfo
（尚无记录）                             ← render_state
（{{chars}} 字，用 state_query 展开）     ← 长值占位
（{{count}} 项，用 state_query 展开）     ← 折叠占位
（本轮无变化）                           ← render_delta
〔没有输入，直接推进〕〔用户插话：…〕      ← goal_manager 的轮次记录
```

它们量不大但每轮都进上下文，而且其中几条是**明确的操作指令**（"用 X 展开"）——
改工具名却忘了改它们，模型就会去调一个不存在的工具。

**它们不做成一个跨 agent 的共用条目，而是分到各自的 agent 名下**，和三个附属提示词
一起归「特殊」。`render_state` 的那几句 director 和 state_manager 都会读到，于是
两份文件里各有一份 —— **这不是"一件事两个入口"**：它们是发给两个不同 agent 的两条
不同消息，本来就该能分别改（director 读 state 是为了推演，state_manager 读它是为了
比对该记什么）。这也正是 D33/D136 那条判据要的形态：**一份文件 = 一个 agent 收到的
全部文字**。

于是每个 agent 都是同样的三块：

| | 装什么 |
|---|---|
| **上下文** | 它收到的那一串消息（三类条目，可拖动排序） |
| **工具** | 它拿得到的工具，每个一条描述（+ 开关，见 §8） |
| **特殊** | 运行时另外追加的整条消息，以及渲染里嵌的短句 |

director 的「特殊」最满：追加输入、空回催促、归段追问、state 渲染、worldinfo 索引提示。
goal_manager 的「特殊」是它那套轮次记录模板。writer 几乎是空的。

**三层的边界**：段落级文字（提示词、工具描述、追问）→ 可编；渲染模板 → 可编，
但它内嵌的值不可编；**数据**（state 的值、正文、细纲）→ 不是提示词，走节点编辑和
世界书那两条路（§4、§5）。

### 页面

```
┌──────────┬────────────────────────────────────────────┐
│ 推演      │ 推演 director              [上下文]  工具   │
│  追加输入 ├────────────────────────────────────────────┤
│  空回     │ ⠿ text    system   你是一位……          ✎  │
│  归段追问 │ ⠿ choice  system   转述与推进  ▾        ✎  │
│ 成文      │ ⠿ text    user     输出契约……           ✎  │
│ 状态      │ ⠿ ctx     user     世界设定                │
│ 目标      │ ⠿ ctx     —        前情                    │
│ 摘要      │ ⠿ ctx     user     当前世界状态             │
│ ──────── │ ⠿ choice  user     事件密度  ▾          ✎  │
│ 渲染文案  │                                            │
└──────────┴────────────────────────────────────────────┘
```

切到「工具」：

```
│ 推演      │ 推演 director               上下文  [工具]  │
│           ├────────────────────────────────────────────┤
│           │ submit_outline                              │
│           │   参数（只读）  outline: string              │
│           │   描述        [交出这一轮的细纲。调用即…]  ✎ │
│           │ ask_question               三档 · medium ▾  │
│           │   参数（只读）  question, options[3]         │
│           │   描述        [……]                      ✎ │
```

### 保存前必须试装配

装配器遇到未知的 `context` 名、缺值的 `{{var}}`、没写 `role` 一律报错（D135 刻意
如此：静默跳过会让一整节悄悄消失）。所以**保存接口拿一份假 session 跑一遍
`assemble`，装不出来就拒绝写盘并报出是哪一节坏了**。否则用户改坏一个字，下一轮
生成直接 500，而错误信息离原因很远。

### 归开发者模式吗

提示词是**部署方写的东西**（D35 的分工），且改坏了整台服务不工作。倾向跟开发者
模式同一个开关（D156 的判据：「这台服务是拿来查问题的还是拿来玩的」）。
**但你日常就在改提示词**，所以这条待定——放开只是去掉一个条件。

## 7. 配置全部上调：每一项落在哪

**session 和 worldbook 不再有"配置"，只有"内容"。** session 装标题、目标、节点树；
worldbook 装名字和条目。所有配置项都归 agent 管理，个别几项归服务。

这不是把设置换个地方摆——它是上一节那条判据的直接推论：**这些开关全都在改
"模型收到什么"**，那就该和提示词在同一页上，而不是散在三个层级里。

### 逐项

| 旧配置 | 原来在 | 去处 |
|---|---|---|
| `input_handling` | ControlDimensions | director 上下文里那个 `choice` 的 `selected` |
| `allow_speaking_for_user` | ControlDimensions | director 的 `speaking_rule` choice |
| `prose_style` / `pov` | ControlDimensions | writer 的两个 choice |
| `expansion_density` | ControlDimensions | **拆成三个独立的 choice**（见下） |
| `model_authority` | ControlDimensions | director 的 `ask_question` **工具描述**那个 choice（D140② 已经搬过去了） |
| `genre_tone` / `content_scale` | WorldMeta | **worldbook 的两条 `world` 条目**（D175）——不是配置，是这个世界写的字 |
| `nudge` | Capabilities | director「特殊」里**空回催促那条的开关** |
| `summarize` auto/manual | Capabilities | director「特殊」里**归段追问那条的开关** |
| `state` | Capabilities | **state_manager 这个 agent 的开关**（左栏上） |
| `state_query` / `worldinfo_read` / `history_search` / `ask_question` | Capabilities | 各自那个工具的开关（工具页） |
| `upstream_runs` | Capabilities | writer 上下文里 `upstream` 那条 `context` 的参数 |
| `state_recent_runs` | Capabilities | state_manager 上下文里 `recent` 那条 `context` 的参数 |
| `trace` | Capabilities | **服务**（见下） |
| `stream` | Capabilities | **服务**（见下） |
| `time_driven` | SessionModes | **留在 session**（见下） |

**几乎每一项都落成"某个具体条目上的开关或参数"** —— 这本身就是它归 agent 管理的
证据：它们从来不是独立的配置，是某条提示词、某个工具、某段 context 的属性。

### 三项不是 agent 行为，但去处不同

| | 去哪 | 为什么 |
|---|---|---|
| `stream` | 服务 | **它关于交付，不关于能力** —— D160 自己就是这么写的（"这是这组里唯一一条关于交付而不是关于能力的"）。开关它不改变模型收到什么，也不改变产出，只改变用户什么时候看到 |
| `trace` | 服务 | 运维。落不落盘跟模型完全无关，D156 已经把采集降为开发者模式 |
| `time_driven` | **session** | 它改的是**触发源**——「**这局故事**没人说话时要不要自己往前跑」。那和 goal 的自动续跑是同一类东西，两者回答的都是"这局故事怎么自己往前走"，所以它和 goal 并列留在 session。尚未实现 |

所以**全局设置分两组**：**界面**（字体、色彩模式）与**服务**（流式、trace、开发者模式）。
后两组本来就是服务级的性质，只是当前错放在 session 上。

### 三处代价，都要写在明处

**① `expansion_density` 拆成三个之后不再同步。** 它现在一个维度喂三处：director 的
`event_density`、writer 的 `density`、goal_manager 的 `pace`。D93 特意让它在两侧读
**两组不同的措辞**（"director 不该知道篇幅"），靠的是同一个取值。上调之后它们是三个
独立的 `selected`，**代码不再保证一致**。

反过来说这也是收益：现在做不到"director 紧凑、writer 铺陈"，之后可以。而"同步"
在这里本来就是个模糊的说法 —— 三段文字讲的是三件事。**降级的是保证，不是能力。**

**② 开关之间的依赖要在页面上表达出来。** 现在有几条是代码里的联动：

- `state` 关 → `state_query` / `state_write` 都不注册
- `state_query` 关 → state **每轮全量注入且长值不截断**（D115：一旦没了展开的路，
  截断就成了有损筛选）

拆成独立开关之后，用户可以关掉 state_manager 却留着 `state_query` —— 于是 director
查一个永远是空的 state。**做法**：agent 关掉时它拥有的工具自动灰掉并注明原因；
D115 那条不是开关而是**渲染规则**，必须保留在代码里（它不是"要不要注册工具"，
是"注入时截不截断"）。

**③ 两局故事不能再有不同的文风。** 题材与尺度不受影响——它们是 worldbook 条目
（D175），跟着世界走。换一套配置的做法是**去 agent 管理改**：那是配置层面的动作，
不是每轮的动作。

**④ 回归集与消融的代价照单收下。** 五个场景各有各的文风（`wangwen` / `gufeng` /
`jishi`），P19 又要求同一批素材跑多档——上调之后一次 bench 只能跑一种文风，
消融改成手动改 YAML。**不为此开一个 `overrides` 后门**：一个"只有程序能用"的
第二取值入口，迟早会有第二个调用者。

文风实验本身没丢：`writer_lab` 走的是**装配之后动消息**那条路（`_terse()` 已经
这么干了），和配置无关。

## 8. YAML 的新形状

一份文件仍然 = **一个 agent 收到的全部文字**（D33/D136）。工具描述搬进来之后
这条判据反而更严整了：以前"全部文字"里漏掉了工具描述那一块。

```yaml
# director.yaml

sections:
  - type: text
    role: system
    body: |
      你必须以非评判性的创作视角……

  - type: choice
    role: user
    name: narration_and_advancement
    selected: narrate_and_advance          # ← 当前选择住在这里（不再在 session 上）
    options:
      narrate_and_advance: |
        将用户输入自然融入叙事……
      narrate_only: |
        ……
      advance_only: ""                     # 空 = 整条不出现

  - type: text
    role: user
    body: |
      本次目标：{{goal}}                    # 单值占位，值为空就删掉这一行

  - type: context
    role: user
    source: worldinfo                      # 只有位置可调，内容是数据
                                           # 题材与尺度也在这里面（D175）

  - type: context
    source: history                        # 前情是一串消息，各自带 role，所以不写 role

tools:
  submit_outline: |
    交出这一轮的细纲。调用即结束这一轮。
  ask_question:                            # 描述本身是一个 choice
    selected: medium
    options:
      low: |
        遇到任何值得由用户决定的分岔都调用它征询。
      medium: |
        ……
      high: |
        ……

# director 的三个附属提示词
append:  [{type: text, role: user, body: "……{{said}}……"}]
nudge:   [{type: text, role: user, body: "……"}]
segment: [{type: text, role: user, body: "本轮已经提交……"}]
```

与现在的差别：

| | 现在 | 之后 |
|---|---|---|
| 条目种类 | `text` / `key` / `context` / `choice` | `text` / `context` / `choice` |
| 条目写法 | `{role: user, title: X, key: y}` —— 键名即类型 | `{type: …, role: …}` —— **类型是显式字段**，拖动排序时要读它 |
| 长文本 | 顶层命名块 + `key` 引用 | 内联进 section |
| 标题 | `title` 自动包标签 | 无，自己写 |
| 选择 | 代码按控制维度给 `options[组名]` | `selected` 写在组里 |
| 工具描述 | Python | `tools:` |
| 片段文件 | `director_append.yaml` 单独一份 | 并进 `director.yaml` 的 `append:` |

**顶层"直接是列表"那条特例可以删掉**（`load()` 里那个 `isinstance(data, list)` 分支）——
它是为片段文件开的，片段并回来之后没有第二个用户。

## 9. 需要后端补的

界面这一轮**绝大部分是纯前端**——§1 那五条能力后端全齐。真正要新增的只有三处：

| 缺口 | 现状 | 要什么 |
|---|---|---|
| 会话列表显示 id | `GET /sessions` 只返回 `list[str]`，界面上是 `sess_a1b2c3…` | 返回卡片：`{id, title, worldbook_id, worldbook_name}` |
| 导入成新设定 | `POST /worldbooks/{id}/import` 必须先有 id | `POST /worldbooks/import` |
| `append` / `remove` 改不了 | `NodePatch` / `EditNode` 只有 `state_set`，落地时 `node.state_delta.set = ...` | 收完整的增量；以及「按结果求差」的入口 |

第三条要说明白：**D96 加 `remove` 正是因为清单要能减**，而现在这两样从界面根本
够不着。「改结果」倾向**后端收期望结果、自己求差**（差分逻辑归 `models/state.py`，
它已经有 `walk` / `paths` / 深合并）——这样「权威是增量」这句话不会被破坏：
接口收到结果的那一刻就把它换算成增量了。

**三条都做完了**（批 2，D176/D177）。落地时另外补了四处，都是做的时候才冒出来的：

| 补的 | 为什么 |
|---|---|
| `siblings` 映射随 `GET /sessions/{id}` 一起给 | 切换器要显示 `⟨2/3⟩` 就得先知道有没有第 2 支；一个节点一次请求会让 20 轮的路径打 20 个请求，而这份数据只在重生成之后才变 |
| `GET …/nodes/{id}/state`（`before` + `values`） | 「改结果」得有起点才能编辑，而那个起点**不是侧栏里的当前状态**——侧栏是路径末端，改历史某一轮时两者不是一个东西 |
| `node_updated` 服务端消息 | `edit_node` 改完什么都不回；改「结果」时落盘的增量是服务端算的，客户端把发出去的东西塞回本地，`state_delta` 就成了旧的 |
| `state_delta` 与 `state_result` 同时给 → 422 | 一起给不知道该听谁的。「我改了结果，它却按指令存了」是查不出来的那种错 |

agent 管理那一页另外要：

| 缺口 | 要什么 |
|---|---|
| 提示词读写 | `GET /agents`（列表）、`GET /agents/{name}`（sections + tools）、`PUT /agents/{name}`（**先试装配再写盘**） |
| 工具参数只读展示 | `GET /agents/{name}` 里带上由 Python 生成的参数 schema |
| 渲染文案 | `GET/PUT /rendering` |

要逐字一致（除了刻意去掉的标签）。和页面混在一起做，出了问题分不清是重构断的
还是页面写错的。

### 「新建无效」犯了两次，第二次的原因完全不同（D179）

批 0 那次是 vite 代理漏了 `/worldbooks`。修完之后同一个症状又来了一次——
而这次 `POST` 是 **200**，设定其实建出来了：

```
POST /worldbooks  -> 200      新建成功
GET  /worldbooks  -> 500      紧接着的列表刷新炸了
```

500 的原因是盘上一条 `kind: "lore"` 的旧条目（那个值早改叫 `world` 了，
`player` 同理——D159 把「用户扮演的角色」从第四种 kind 改成了角色条目加一个标记，
**两次改形状都漏了迁移**）。列表接口遍历条目去数「几条」，一条读不出来就整个 500。

而 `create()` 只有 `try/finally`：异常静默消失，界面看起来什么都没发生。

**三层修法，每一层单独成立**：

| 层 | 修法 |
|---|---|
| 数据 | `Store.migrate_kinds()`，启动时跑一次。读原始 JSON——这些值现在根本不在 `EntryKind` 里，用模型去读要修的数据是个死结 |
| 读取 | 分层：喂模型的 `entries()` **照旧严格抛**（悄悄少一条设定比 500 坏得多，D62）；只为显示的 `survey()` 宽容，好的照数、坏的**点出来** |
| 界面 | 每个动作包进 `guard()`，出错显示在页头。**一个只会抛不会显示的错误，和不报错没有区别** |

### 第 0 批那个 bug 值得记下来

`vite.config.ts` 的代理只写了 `/sessions` 和 `/meta`，**漏了 `/worldbooks`**。
于是 dev 下所有 `/worldbooks` 请求打到 Vite 自己的 dev server，返回 `index.html`
**且状态码 200**——`res.ok` 为真，`res.json()` 解析 HTML 才抛，而调用处没有 catch，
异常静默消失。症状是「列表恒空、新建无反应」，而后端和测试全绿。

**教训不是"记得改代理"，是"前端的失败要出声"**：`api.ts` 的 `json()` helper
只在 `!res.ok` 时抛，应当同时校验 `content-type`——拿到 HTML 就是配置错了，
那比解析失败更早、也更好懂。
