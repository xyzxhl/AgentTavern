# 检索与渐进式披露

> 什么时候可以用规则、什么时候只能交给模型。术语定义在 [../Glossary.md](../Glossary.md)，这里复述判别式因为它是全文的前提。

## 1. 术语

三样东西必须区分，判别式是**谁改变它**：

| 术语 | 内容 | 由谁改变 |
|---|---|---|
| **state** | 结构化的世界当前状态：在场、时间、地点、谁知道什么、关系、伏笔状态 + 自由 KV | **剧情推进**（director 每 run 提交增量） |
| **worldinfo** | 静态设定：角色卡、世界观、背景 | **用户**（元操作"改设定"） |
| **history** | 过往 run 的细纲 | 每 run 追加，只增不改 |

**`ledger`、`账本`、`后台数据` 三词已废弃。** 工具名为 `state_query`，参数名为 `state_delta`。

灰区说明：同一实体可两边都有——"他们是兄妹"属 worldinfo，"他们现在决裂了"属 state。

## 2. 核心难点：信息需求在推演过程中才产生

**某角色出场 → 需要他的信息；但"他出场"是 director 在推演中才决定的。**

代码无法预判，因为决定尚未做出。这使得预取（push）在**实体级信息**上本质受限——它只对**固定核心维度**成立（在场、时间、地点：体量小、恒定相关、可无条件注入）。

此前曾表述为"结构化化解了 push/pull 边界问题的大半"，**过于乐观**：化解的只是固定核心那部分，实体级检索完全没被化解。

## 3. 准入标准：规则可以做无损降维，不能做有损筛选

智能检索与规则检索可以共存，**但规则的范围必须受限于"在所有情况下都不会出错"的设计**。可操作的判据：

> **分界线是模型是否知道自己缺了什么。**

| | 合格 | 不合格 |
|---|---|---|
| 规则做什么 | 覆盖**全集**，只调节精度 | 筛选**子集**，猜相关性 |
| 失败模式 | 信息不够细 | 信息完全缺失 |
| 模型知情 | ✓ 摘要在眼前，知道可以展开 | ✗ 根本没意识到存在 |
| 可自愈 | ✓ 点查补救 | ✗ |

### 案例复核

**history 摘要分层 —— 合格。** 规则只做"压缩率随距离递减"，**不做相关性判断**：全部历史都在，只是远的以摘要形式呈现。相关性判断留给模型，而模型手里有摘要，知道该展开哪段。

**worldinfo 全量索引 —— 合格。** 同一模式：全部条目的索引（名称 + 摘要 + 体量）注入，正文按需拉取。

**时间局部性预取 —— 不合格，已出局。** "上一 run 涉及的实体，这一 run 大概率仍相关"——它在猜相关性，场景切换即带错人，且模型不知道有角色信息没被带入。

**lorebook 关键词触发 —— 不合格。** 同一失败模式：关键词漏命中 → 条目完全缺失 → 模型不知道有这个设定存在。这比"漏命中"的表述更准确地说明了它为何是坏设计。

**注意 TauriTavern 的两阶段只做对了一半**：其 `worldinfo_read_activated` 的索引只覆盖"已被关键词激活的"条目，底层仍是筛选子集。合格的做法是索引覆盖**全部**条目。

## 4. 由此得到的统一方案：全量索引 + 按需展开

worldinfo 与 history 用的是**同一个模式**，不是两套：

```
注入：全部条目的索引（标识 + 摘要 + 体量）
     + 近期条目的全文
工具：按标识拉取正文，支持范围分页
```

索引中**必须带体量**，让模型知道拉全文的代价。

**摘要由 `summarize` 工具懒惰生成**（[Tools.md](Tools.md) §5）：模型在实际需要压缩时调用，系统缓存复用，不预先批量产生。尚无摘要的条目回退到"前 N 字 + 字数"——仍满足 D62，只是精度低一点。

**仍未验证**：索引本身在规模很大时（几百个实体）是否会撑爆；场景切换时的表现。这部分需要实测。

### 早期开发的验收标准：调得动就行

**检索三者（state / worldinfo / history）都不是早期必须做到完美的东西。** 验收标准只有一条：**工具注册了，模型在需要时调得动。不做查准 / 查全要求。**

理由是它在系统里的位置——检索是 state 与摘要的**兜底**，不是常规路径：

- state 记着会约束后续的东西与还欠着的账（D109）
- 摘要按"可不可再生"取舍，具体项优先留下（D110）
- 剩下真正漏掉的，才轮到检索

**前两条越准，兜底被用到的次数越少。** 实测里检索多次"正确地闲置"——摘要保住了要找的信息，模型不必去翻。**那是系统健康的表现，不是覆盖不足。** 在这种前提下追检索的查准查全，是在优化一条很少走的路。

因此这一层的投入到此为止：工具面正确、语义不误导（见下面两条已修的缺陷）、关掉时行为明确（D115）。**真正该继续投的是 summarize**——它决定兜底要被用到多少次。

### 什么时候 state 和摘要不够，非读原文不可

这条判据决定了 `history_search` / `history_read` 的工具描述该怎么写——**说清机制没有用，要说清触发条件**。

两者的盲区是**同一个**：

| | 保留了什么 | 因此丢了什么 |
|---|---|---|
| **state** | 只记**会约束后续**的东西（D95） | 一切当下不构成约束的具体细节 |
| **摘要** | 写它那一刻认为重要的东西 | 当时看着不重要的东西 |

**两者的交集盲区，就是「当时不要紧、现在才要紧」的细节。** 而这恰恰是长篇最要命的一类——**伏笔的价值天生是延迟显现的**：埋下去的那一刻它什么也不约束（进不了 state），也不是那一轮的重点（进不了摘要）。写摘要时无从知道它以后会重要，这不是摘要写得不好，是**原理上做不到**。

由此得到六条触发条件：

| 情形 | 为什么 state 和摘要都不行 |
|---|---|
| 要**引用早前的原话** | state 里根本没有原话（D67）；摘要会改写措辞 |
| 要**兑现或推翻一个伏笔** | 埋下时它两边都进不去 |
| 要说清**先后与因果** | state 只有此刻的值；摘要把顺序压平了 |
| **摘要与 state 对不上** | 摘要是压缩过的，可能有损；冲突时以原文为准 |
| 用户**直接指某一轮** | "回到他们在酒店那次" |
| 怀疑**与早前矛盾但说不清哪里** | 这是"不知道自己漏了什么"，只能扫 |

反面同样要写，否则会滥用（每轮翻史，token 爆炸）：**想知道现在是什么样**看 state；**想接住上一轮的语气**——近几轮细纲已经在上下文里；**只想知道大概发生过什么**——摘要够用。

正反对照着说，边界才钉得住（同 D35 的理由）。

### 造一个能压到检索层的探针，比修检索层本身难

探针改了三版才成立，每一版的失效方式都是一条独立的教训：

| 版本 | 做法 | 为什么测不到 |
|---|---|---|
| 一 | 追问「三年前七月那天，你在哪」 | **问句里含着答案**，模型不必检索 |
| 二 | 埋点落在第 2 轮细纲开头 | 索引回退是"前 120 字"，**原样泄漏**。这一版顺带暴露了 `summarize` 从未启用 |
| 三 | 埋「那天你在哪」的**直接答案**（一个地名） | 摘要把它完整保住了，模型直接用上——**检索正确地闲置** |

第三版尤其要说清：那**不是失败**。摘要没丢东西，渐进式披露按设计工作，检索本就不该被调用。失败的是探针——它测的东西不存在。

由此得到探针的真正条件，**而它就是上一节那条判据本身**：

> **埋下去的东西，当时必须不要紧。**

摘要保留的是"人物、地点、关键事件与因果"，所以埋点必须落在这四样之外：一个背景细节、一行无关的字、一件没人在意的物件。只有这种东西才会**既进不了 state**（不约束后续）、**也留不住在摘要里**（不是当时的重点）——那正是两者的交集盲区。

现在埋的是柜台上一本台账的一行字（`7月12日 收 座钟一台 王`），追问时只说「你台账最上面那一行」。

**这件事本身是个方法论警告**：一个覆盖不到的组件，最容易的失败方式不是"测出问题"，而是"测出一切正常"。

### 两个实现缺陷，它们解释了这层为何从未被调用过

**首要原因其实平淡得多，而且是测试自己的错**：检索默认关闭（D78；开关现在是 `director.yaml` 里 `tools.history_search.enabled`，D174），而回归集的场景没打开它——**那 12 轮里两个工具根本没有被注册**。同理归段追问关掉时 `summarize` 工具也不注册。所以"12 轮一次都没调用"这个观察什么也说明不了。

> **被测的东西没有启用，而结果看起来像一个发现。** 这类错误比测出问题更危险——它给的是虚假的安全感，而且会引出一整串建立在假前提上的分析。

下面两处是代码审查发现的真缺陷，它们值得修，但**不是**未被调用的原因：

1. **注入的索引不带 ref。** 历史索引写的是「第 N 轮」，而 `history_read` 要的是 run id——**模型看得见索引，却拿它没办法**，必须先花一轮 `history_search` 换 id。对比之下 worldinfo 的索引一直带 ref，`worldinfo_read` 也一直被正常调用。差别就在这一处。
2. **`history_search` 的 `query` 是子串过滤器，违反 §3。** 查不中就返回空列表，而模型会把"空"读成"没这回事"——**这正是判 lorebook 关键词触发不合格的那条理由，我们自己却犯了**。而且伏笔常常换了个说法，逐字查不中是常态不是例外。现已改为：索引永远覆盖全部轮次，命中的只多一个标记，并在结果里明写"没命中不等于没发生过"。

第二条值得单独记：**同一个错误换了个位置就没认出来。** §3 那条准入标准是我们自己定的，批评别人的实现时用得很顺手，写自己的检索工具时却漏掉了。

## 5. 写入侧：乐观处理 + 用户参与维护

写入与检索的**风险不对称**：

- **检索遗漏可自愈**——这次没查到，下次还能查。
- **提取遗漏不可自愈**——这一 run 漏记了"她知道了真相"，之后永久丢失，因为 **director 不读正文**，没有任何机制能回捞。

D19 强制每 run 提交增量只解决"有没有提交"，解决不了"提交得全不全"，而后者代码查不出来（D30）。

**结论：不用系统机制解决，改为乐观处理 + 让用户参与维护。**

> **state 必须是用户可随时查看 / 编辑的。**

这不只是兜底，**state 可见本身就是产品价值**：用户看到"她知道真相：是"这一行，既能纠错，也能理解当前剧情状态。现有工具完全没有这一层。

三项连带要求：

1. **state 必须人类可读**，不能是内部编码。
2. **用户编辑要进 trace**——它是一次状态变更，且来源是用户。
3. **用户编辑直接修改节点数据，不做依赖检查。**

关于第 3 点：**state、细纲、正文三者都可编辑，编辑即直接改写该节点的数据，无视对下游的破坏**——乐观假设用户只修改最新输出的内容，此时本就没有下游。

这与 D48（状态是路径的函数）不冲突：改了节点的 `state_delta`，重放路径时自然生效。此前曾主张"插入一个只含 delta 的新节点"以保护已提交节点的不可变性，**该方案已否决**——它为一个乐观假设下不存在的问题增加了结构复杂度，也不符合常见 AI chat 的编辑语义。
