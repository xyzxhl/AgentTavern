# 非轮次形态

> 对应 [Decisions.md](../Decisions.md) Q6。**非轮次是探索方向而非确定设计**（D5），判据是用户体验是否真的改变，而非表面是否还存在 run 的概念。

## 1. 生成器：轮次式的六个属性

打破其中任一条，即得到一类非轮次形态。用于系统性地寻找候选，而非穷举清单。

| | 轮次式属性 | 打破后 |
|---|---|---|
| P1 | 一次输入对应一次输出（1:1） | 长循环（1:N）／消息排队（N:1） |
| P2 | 用户输入是唯一触发器 | 时间触发、状态触发 |
| P3 | 生成是原子的，中途不可干预 | 打断、注入、中途分叉 |
| P4 | 输出即终态，只能重 roll | 追加提交、局部重生成、就地修订 |
| P5 | 用户等待时无事可做 | 并行候选、等待期可改设定 |
| P6 | 只有一条时间线 | 多线并行 |

## 2. 核心统一：三种形态是同一个旋钮的三档

长循环、整个输出多候选、交互式创作（拆小任务逐节点选择）——**不是三种形态，是一个机制的三个档位**。机制是"停下来给选项让用户选"，变量只有频率。

| 形态 | 一个 run 内 `ask_question` 的调用次数 |
|---|---|
| 长循环自主创作 | 0 次，由 goal 驱动连续多个 run |
| 整个输出多候选 | 约 1 次（细纲成型后给候选） |
| 交互式创作 | 多次，边推演边问 |

**三档均保持 run ↔ 细纲一一对应**——交互式创作是在**一个 run 内**多次提问，而非拆成多个 run。见 [Architecture.md](Architecture.md) §7。

该频率**就是**模型剧情控制权这一控制维度的操作化定义。落到实现上：**控制权等级直接反映为调用 `ask_question` 工具的积极性——控制权越高，调用积极性越低**（D39）。它是倾向而非硬计数，但 `ask_question` 的调用频率在 trace 里直接可观测，各档位表现可测量校准。见 [Configuration.md](Configuration.md)。

三点推论：

1. **不需要为三种形态各做一套**：一套机制 + 一个频率参数即可。
2. **"分叉点由谁决定"解决了一半**：频率由用户设定的等级给出，模型只需在给定频率约束下挑**相对最好**的位置，而非自由判断"这里该不该分叉"。这是 [../Principles.md](../Principles.md) P10 的一次应用。
3. **A3 控制权交回是同一机制的另一种触发**：频率驱动（到点就问）vs 条件驱动（信息不足才问）。二者可共用同一套 UI 与协议。

## 3. 用户中途输入的两种语义

**必须区分，且必须显式化。**

| | 含义 | 时机 | 成本 |
|---|---|---|---|
| **立刻介入当前 loop** | 纠正——"不对，别这么写" | 中断当前生成，改变正在产出的内容 | 高：需 cancellation 贯穿整条 loop，且需决定已生成部分如何处理（丢弃 / 保留为"被打断的话"） |
| **进入下一个 loop（排队）** | 推进——"然后我要说……" | 不影响当前产出，作为后续轮次的输入 | 近零：一个队列 |

- **显式化**：按 D15，UI 上应是两种不同的提交方式（两个按钮，或不同快捷键），不让系统推断这句话是纠正还是推进。
- **分开排期**：成本差一个数量级，不应因"都是用户中途输入"而当作同一个功能实现。

### 排队必须逐条消费，不得打包

队列是 **FIFO，每条输入独立成一个 run**。多条排队内容**不可合并为单次输入**。

理由：**RP 中每个用户动作都需要独立的世界响应。** 用户连发"我推开门"/"我环顾四周"/"我叫了一声"，打包会变成"你推开门环顾四周叫了一声，然后……"——跳过了中间信息，而推开门看到什么本应影响要不要叫。

打包本质上是 [InputHandling.md](InputHandling.md) §2 中 P1 漏转述 / P2 覆盖不全的一个变体：用户输入被压缩处理。它还会破坏 D19——每 run 一个状态增量，打包后只剩一个，中间状态全丢。

两个衍生设计点：

- 用户应能看到队列中待处理的输入，并可撤销 / 编辑尚未消费的部分。
- **队列非空时，模型的自主推进应暂停。** 否则控制权等级高时模型自行跑了数个 run，用户排队的输入被消费时已经过时。**用户输入优先于自主推进**，倾向定死而非做成可配置。

## 4. 候选形态评估

| 形态 | 评估 | 位置 |
|---|---|---|
| **消息排队** | 真实聊天本就如此，现有 RP 工具全部强制一问一答。架构成本近零 | 优先做 |
| **呈现 agent 工作过程** | 把延迟从"卡顿"变成"沉浸"——工具轨迹是世界在运转的证据。归 **UI/UX**，本就该做。架构侧残留见 §5 | 优先做 |
| **并行候选 / 交互式创作** | 现有 airp 产品已有类似功能，开发成本不高。粒度问题由 §2 统一解决。**成本反直觉**：用户本就常重 roll 2–3 次，串行重 roll 三次与并行三候选 token 成本相当，但体感延迟只有 1/3，且是比较中选而非盲抽——正好对冲 D7 放弃流式的代价 | 值得做 |
| **局部重生成** | AI 写作软件已有类似功能。**贵在影响面计算**而非生成——改了第 3 段，后续哪几段依赖它、state 哪些条目要回滚。无结构化状态基本做不了；有 D18 后可行但仍不便宜 | 排在 state 落地之后 |
| **时间驱动（静默触发）** | 用户静默 N 秒后角色主动开口，体验冲击最大——角色第一次"活了"。可做**轻量版**：只让在场角色做小动作或开口，**不推进剧情**、不做后台世界模拟，成本比完整自主演化低一个数量级。必须给用户开关——它是**模式**而非控制维度（D38），见 [Configuration.md](Configuration.md) §3 | 可考虑，靠后 |

## 5. 明确避开

- **多时间线并行推进（P6）**：认知负担极高，用户会迷失。分支应当是**回溯时才产生**的，而非同时维护。
- **生成中实时调旋钮（P3）**：用户在阅读时不会去动它。
- **支线后台推进**：即完整的自主演化，成本已判为不划算（D14）。

## 5.5 长任务的终止：goal 终止条件

用户设置可判定的标准。机制：**正常一轮生成结束后检查是否达标，未达标则开启下一轮。**

**goal 不是模式**——有无 goal 系统跑法一样，只是轮末多一个判定。它归 Session 元指令（[Configuration.md](Configuration.md) §1）。与控制权等级也不冲突：控制权作用在**轮内**（是否停下来问），goal 作用在**轮末**（是否再开一轮），可任意组合。



**达标判定一律交给模型，不降级为代码判定。**

此处曾主张把目标绑到结构化维度上做代码判定（关系状态 = 决裂、伏笔 = 已兑现等），**这是错的**：这些字段的值本就是模型写进去的（D18），代码读取比对的只是模型早已做完的判断。语义判断发生在**写入时**，代码检查发生在**读取时**——它不是独立验证器，只是一次查表，把模型的判断包装成代码的样子，不增加任何保证。D19「代码只管契约完整性」才是一致的立场。

不降级不等于听天由命，另有两个杠杆：

**一、目标表述的具体化。** 用户设的标准越具体可判，模型判定越准。同 [../Principles.md](../Principles.md) P20「防过早宣告胜利」的手法：具体标准 + "必须完成全部检查"的显式指令。这是契约设计的杠杆，不是代码的。

**二、独立的、干净上下文的判定调用。** goal 达标判定是 D17 判别式（上下文差 × 验证器）**两个条件罕见地都满足**的场合：

- **有验证器**：用户设定的目标就是明确给定的真值。
- **有上下文差**：判定只需要 [目标 + 已产出内容摘要]，完全不需要创作过程。

因此值得用一次独立调用，而非让生成模型顺手判断——生成模型知道自己想怎么写，会往"已经达标"的方向读。

这不复活 critic：频率极低（每 N 个 run 一次）、上下文极短、输出为 yes/no，成本可忽略。D17 说的是"残余不够养一个独立组件"，而这是一次窄调用，不是组件。

> **后续修正（D148）：它已经不是窄调用了。** 上面这段推理里"只需要 [目标 + 已产出内容摘要]"这一条不成立——判定与**重拆计划**是同一次判断的两面（"哪些达成了"和"剩下的还成不成立"），而重拆随时可能发生，不能等"名义上走完全部阶段"。所以现在它是 `goal_manager`：一份跨整个 goal 生命周期的长对话，静态前缀不变、每轮追加一条"第 N 轮发生了什么"，四个工具（`plan` / `check` / `steer` / `finish`）由模型自己决定这一轮调哪几个。
>
> **保住的是"独立上下文"那一条**：它读的仍然不是 director 的创作过程，而是逐轮的结果。生成模型会往"已经达标"的方向读，这个理由没变。
>
> **终态只有 `done` / `failed`**，预算耗尽是**暂停**不是失败——用户可以加预算接着跑。

**必须有硬上限保底**：模型可能永远判不达标，或目标本身不可达。goal + token / run 上限双保险。同 [../Principles.md](../Principles.md) P16–P17"每个子 agent 设 token 预算上限"。

**goal 与 §2 的频率旋钮正交**（D40）：goal 决定整个长任务何时结束，频率决定过程中多久停下来问一次。一个管终点，一个管节奏。二者的 2×2 组合见 [Configuration.md](Configuration.md) §4——**长循环自主创作 = 高控制权 + 有 goal**，是参数取值而非独立模式。

## 6. 架构侧残留要求：trace 分两层

"呈现 agent 工作过程"归 UI/UX，但**用于 eval 的 trace 与用于 UI 呈现的消息是两件事**，必须分层：

| | 目标 | 特征 |
|---|---|---|
| **Trace（eval 用）** | 可回放、可统计、可归因（D8） | 完整、机器可读、不筛选 |
| **UI 呈现** | 沉浸感、可理解 | trace 的**投影**：选哪些事件 + 渲染成人话 |

两条约束：

1. **trace 必须携带足够的语义信息使投影可行。** 若只记 `state_query(dimension=..., subject=...)`，事后无论如何也渲染不出"确认了她现在在哪"。这部分必须在 trace 设计时纳入，事后补代价很高。
2. **筛选规则与渲染模板属于 UI 层，不得污染 trace schema。** 否则 trace 会被 UI 需求牵着走，eval 时反而缺字段。
