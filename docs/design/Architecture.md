# 架构

> 组件、时序、职责覆盖。拆分的**论证**见 [Generation.md](Generation.md)，判据见 [../Principles.md](../Principles.md)。

## 1. 拓扑

```
编排层（代码，静态 workflow）
  ├─ director（主 agent，tool loop）
  │     产出：细纲（无文风约束的文章）
  │
  │     ── 固定、单向的交接 ──▶
  │
  ├─ writer（纯渲染，单次调用）
  │     产出：正文 + 偏离报告
  │
  ├─ state_manager（tool loop，run 末，读细纲 + 正文）
  │     产出：状态增量
  │
  └─ goal_manager（tool loop，跨 run 的长对话，仅长任务，run 末）
        产出：下一条输入 / 目标终态
```

**director 是主 agent**，拿走全部推演职责。**writer 是从主 agent 身上拆下来的一个负担**——它只承担文风，不是流水线的下游规划环节（D52）。

**state_manager 是第三个 agent**（D143）。状态维护本来挂在 director 身上，现在拆出来后置：它读**刚写完的细纲和正文**再记，于是 writer 的产出得以回流进状态——而这条回流不违反 D54，因为它跨了 run 边界、且经过一次有损压缩（正文折成键值），不是把正文塞回 director 的上下文。

**goal_manager 不是"窄调用"**（D148）。它曾经是 run 末一次干净的 yes/no 判定，现在是一份**跨整个 goal 生命周期的长对话**：静态前缀不变，每轮追加一条"第 N 轮发生了什么"，模型自己决定这一轮调哪几个工具。改的原因是 plan-then-execute 挡不住剧情偏移——重拆计划的时机必须由它自己判断，而不是等"名义上走完全部阶段"。

## 2. 交接是静态 workflow，不是工具调用

编排层按固定顺序调用二者，中间没有回流、没有协商、没有重试循环（D53）。

### writer 绝不能做成 director 的 tool

把 writer 写成 `render(细纲) → 正文` 看起来很自然，但**工具返回值会回流到调用者的上下文**——正文一旦回流到 director，整个隔离设计就没了。

director 之所以能覆盖五倍跨度的历史，正是因为它**从不读正文**。**这条一破，[Generation.md](Generation.md) 的全部论证作废**（D54）。

## 3. 职责划分

| | director | writer | state_manager |
|---|---|---|---|
| 形态 | tool loop | 单次调用 | tool loop |
| state | **默认包（值）** + 点查工具 | **完全没有** | 全量当前状态 + 前 k 轮更新记录 |
| 历史 | 细纲历史 | 正文上文（n 轮，衔接用） | 前 k 轮的细纲 + 正文 |
| 世界设定 | ✓ | ✗ | ✗ |
| 文风 / 角色语言习惯 | ✗ | ✓ | ✗ |
| 读正文 | ✗ | —— | ✓ 只读**本轮**与前 k 轮 |
| 写 state | ✗ | ✗ | ✓ **唯一写者** |
| `ask_question` | ✓ | ✗ | ✗ |
| 产出 | 细纲 | 正文 + 偏离报告 | 状态增量 |

**没有「否定项」这一行了**（D139）。它曾经是 session 上的一个字段，两侧都注入。删掉的理由是它给同一件事开了第三个入口：不能提前揭示的东西属于世界设定（写进 worldinfo 或 state），「不许写什么」这类写作纪律属于提示词（写进 YAML）。

`n` 与 `k` 都是用户可调的窗口（`upstream_runs` / `state_recent_runs`），默认各 3。

**writer 不添细节。** 细节的责任在 director——细纲是"无文风约束的文章"（D34），实体细节本就该在里面；细纲没写的，否定项中"不允许发明"已覆盖（D35）。

这强化了细纲的粒度下限 = **映射无歧义** 且 **包含全部实体细节**，两个要求指向同一个下限。

## 4. 一个 run 的时序

```
1. 编排：取队列头一条输入（FIFO，不打包，D26）
2. 编排：按能力开关组装工具面（关闭的能力其工具不注册）
     **控制维度也要传进去**——ask_question 的调用积极性写在它自己的
     工具描述里，按 model_authority 分三档（D39/D58/D155）
3. 编排：装配 director 上下文
     细纲历史 + 世界设定 + state 默认包 + 用户指令 + 元指令 + 控制维度
4. director tool loop
     → 细纲（唯一终止点是 submit_outline）
5. 编排：装配 writer 上下文
     细纲 + 正文上文（n 轮）+ 文风 + 角色语言习惯
6. writer → 正文 + 偏离报告
7. state_manager tool loop（读本轮细纲 + 正文 + 前 k 轮记录）
     → 状态增量（收口条件：这一次不再调用任何工具）
8. 代码：eval 采样标记 → 只提示，不拦截
9. 代码：commit 暂存增量、落节点、落 trace（仅开发者模式）
10. 编排：归段追问（生成后，问刚写完的 director 本人）→ 需要则压缩成摘要
11. 编排：有 goal 则 run 末跑一轮 goal_manager → 未达标则用它写的输入开下一 run
```

**第 7 步卡在第 9 步之前不是随意的**：节点是原子的，细纲、正文、增量必须同时抵达（D48/D56）。放到落盘之后会出现一个"有正文没增量"的瞬时节点，那一刻沿路径重放状态的人（分支、`state_at`）会算错。代价是这一轮的结束晚一次模型调用，而用户此时已经看完正文了。

**第 7 步没有前置契约**。这里曾有 E0：`submit_outline` 之前必须至少调用过一次 `state_write`，空增量合法，用来区分「确实没变化」与「模型忘了提交」。director 卸下 `state_write` 之后它自然作废（D143）。

每 run 三次主调用（director 的 tool 往返、归段追问、goal_manager 另计）。

## 5. state 写入：state_manager 单点，run 内暂存，run 末原子提交

**由 state_manager 通过工具写入**（D143）。这条改过一次：原先是 director 边推演边写（D55），理由是它有完整的 state 上下文、知道该往哪个键写。**写入单线程（P5）这一点没变，变的是谁是那个单点。**

后置的理由是**它该读的东西在 writer 之后才存在**：细纲只说定了什么，正文才是最终写出来的——留白处落成了什么、话说到什么份上，只有正文看得见。让 director 边推演边记，等于让它照着自己的计划记账，而不是照着实际发生的记。

它每轮拿到：全量当前状态、前 k 轮的（细纲 + 正文 + 当时记下的增量）、本轮的细纲与正文。带上前 k 轮的更新记录是为了**工具调用的一致性**——键名怎么起、粒度多粗，看几个例子比讲判据管用。

`state_write` 可在 loop 中多次调用，写入进 run 内暂存区，**run 完整结束时一并 commit**（D56），与 D48（节点原子）一致。

**state 能力关闭时 state_manager 整个不跑**（D80）。

## 6. 偏离报告

writer 若为通顺而增删了实质内容，输出**偏离报告**（通常为空，D57）。编排层将其附在节点上，下一 run 的 director 读细纲历史时可见。

「细纲更新为实际发生的」由此落地：责任是 **writer 报告、编排层记录**，而非 writer 改写细纲。writer 保持纯粹。

## 7. 打断的单位是阶段

三个阶段各自为界。**掐到哪一段，哪一段就判为失败、产出作废**；它的上游都已完成，存进草稿等续跑（D142）。

| 阶段 | 处理 |
|---|---|
| director | 推演存成草稿（含已查到的资料、已提交过的细纲），细纲不算数 |
| writer | **半截正文不留**，细纲进草稿 |
| state | 已经写下的那几笔算数（是已完成的动作），细纲与正文进草稿 |

**恢复点由下一次输入是否为空决定**：空输入 = 只重跑被掐掉的那一段；有输入 = 回 director 重来，因为用户的话可能改细纲，之前生成的内容都不再可信。回 director 时轮数归零，追加的输入接在 `submit_outline` 之后——它表达的正是「对上一版细纲不满意」。

**这一条推翻了 D60。** D60 主张 writer 阶段保留已生成的片段，理由是"话说了一半被打断"在 RP 里是真实感的来源。实际不是：留着它，下一轮会接着那半句往下写，而用户按停止恰恰是因为不想要那半句。`RunStatus.PARTIAL` 随之删除。

## 8. 归因五类

| 归因 | 症状 | 修法 |
|---|---|---|
| director 检索不足 | 细纲与 state 矛盾 | 改默认包覆盖 / 键名 |
| director 推演错 | 细纲与用户指令不符（漏转述、覆盖不全） | 改 director 契约 |
| writer 偏离细纲 | 正文与细纲不符 | 改 writer 契约 / 细纲粒度 |
| writer 文风失败 | 符合细纲但读起来不对 | 改文风约束 |
| 写入遗漏 | 增量与正文不符 | 改写入契约 |

五类**都能从 trace 直接判定**，因为每一步的输入输出都物化了，且细纲是散文、可直接与正文比对。

**归因的可行性正是 director/writer 拆分的副产品**——合并方案下无法区分"规划错了"与"执行错了"。

## 9. 职责覆盖表

一份"这件事必须有人做"的清单，用于检查没有工作掉在地上。每项标注归属。

| 工作 | 归属 |
|---|---|
| 确定本轮的控制维度取值 | 用户显式设置，编排层读取 |
| 分离元操作与内容输入 | 编排层 / 协议 |
| 停下来给选项、等待用户回答 | director（`ask_question`，题干 + 恰好三个选项，用户也可自由作答） |
| 把输入补全成细纲 | director |
| 无用户输入时自产输入 | goal_manager（`steer` 写下一条，标注为 `simulated`） |
| 长任务的拆解、进度核对与终止判定 | goal_manager（跨 run 的长对话） |
| state 写入 | state_manager，唯一写者 |
| 判定一段剧情收没收 | director 本人（生成后追问，不是冷调用） |
| 把收了的那一段压成摘要 | 编排层（`summarize`，段收即压） |
| state 检索 · 默认包 | 编排层无条件注入 |
| state 检索 · 点查 | director（`state_query`） |
| 语义判断（伏笔是否兑现等） | director |
| 按文风改写为正文 | writer |
| 报告实质偏离 | writer |
| 内容的提交与呈现 | 编排层 |
| eval 采样标记 | 代码 |
| trace 采集 | 编排层（开发者模式） |
| trace → UI 投影 | UI 层，从 trace 事件派生 |
| 回滚与分支 | 编排层 + 存储 |
| 排队与打断 | SessionRunner |
| 成本可见性 | 实时推送，用户手动打断 |

**代码不做的**：任何需要理解内容含义的判断。结构性交叉比对经落地确认在本项目里不成立，已取消——详见 [State.md](State.md)。

## 10. 未定

| 议题 | 状态 |
|---|---|
| 渐进式披露的规模表现 | 方案已定，未验证：索引在几百实体下是否撑爆、场景切换时的表现 |
| 实体级检索的鸡生蛋 | **信息需求在推演中才产生**这一根本问题未解——P13 只划定了规则的边界，边界外交给模型主动点查 |
| 文风的结构层能否留在 writer 侧 | 转入实验（[Generation.md](Generation.md) §9） |
| 细纲的粒度下限 | 转入实验，与上一条是同一张力的两端。**实测已成问题**：`chapters` 场景 12 轮里 `ratio_avg` 只有 1.21、最低 0.70（正文比细纲还短），细纲里出现了描写 |
| F3b「立刻介入当前 loop」 | **已实现**（D119）。插入点在操作边界上——一次模型调用或一次工具调用之间，不是等这一轮写完；`interrupt=True` 掐掉在飞的那次操作，`False` 让它做完再插 |
| 摘要替换那条路 | 摘要生成与分界判定都已实测（`chapters` 查全查准均 1.00），但**「越界后换成摘要」从未被真实模型触发过**——12 轮扁平化才 14351 字，`budget_chars` 是 96000，只占 15% |
| `ask_question` 的触发率 | 形状与采纳都验过了，但在刻意造出的设定冲突上、`model_authority=low` 时，9 次里只问 3 次。分岔存不存在取决于这一次模型的取舍 |
| goal 面板的暂停 / 加预算 / 放弃 | 后端每条都有测试，**但从未在真实模型下走完一遍**——单轮约 6 分钟，一个完整 goal 跑不完。启动侧的几种情形（0 轮、运行中设、判定期间放弃）已在 D164–D166 这一轮补齐并各有一条会红的测试 |
| 落地之后留着的思考段 | 过程分片现在跨 `run_finished` 保留（D166），**内存里是无界的**：一轮 director 的思考段实测两万余字，几十轮的会话会攒下几 MB 字符串。刷新页面即清空，所以还没成问题；真成问题时的出口是只留最近 N 轮 |
