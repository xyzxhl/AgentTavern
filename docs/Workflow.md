# 工作约定

> 这份文档管的是**改动怎么落地**，不是系统怎么设计。
>
> **主要读者是模型**（包括我自己下一次开会话时）。人也照这个来。

## 三层

每层回答一个问题，每层配一条**能当场判**的判别式——写下一句话时就知道它该去哪。

| | 回答 | 住在 | 判别式 |
|---|---|---|---|
| **req** | 用户要什么 | `req/` | **用户读不懂，它就不是 req** |
| **spec** | 系统做什么 | `spec/` | **写不出一条会红的测试，它就不是 spec** |
| **test** | 怎么证明做到了 | `backend/tests/` | **删掉一条断言 = 放弃一条 spec** |

`spec` 是**唯一权威**：代码和 req 打架时，以 spec 为准，或者改 spec。

判别式不是修辞。「用户读不懂」当场排掉「节点树按路径重放状态」这种混进 req 的机制；
「写不出测试」当场排掉散文——一句话若写不出验收，它要么是 req，要么是论证，要么根本没想清楚。

### 「为什么」不是一层

反方案为什么不行、踩过什么坑，是 **req 和 spec 每一条自带的字段**，不独立成层。

只有**跨条目复用的判断法**例外——「模型的开放判断一律降级为受约束的选择」这种，
它不服务任何单条 spec，而是**从 req 推 spec 时用的工具**。这些住在
[Principles.md](Principles.md)，编号 `P<n>`。

## 编号

| | 是什么 | 由谁定 |
|---|---|---|
| `R<n>` | 一条需求 | 我加工，你可随时改 |
| `S<n>` | 一条规格 | 我写 |
| `P<n>` | 一条判断法 | 我写 |

**编号永不复用、永不重排。** 代码注释、测试 docstring、文档正文都靠编号找到它，
重排会让所有引用同时失效且不报错。

废弃一条就划掉标题（`~~S42~~`），说明改写成**现在的做法**，再给取代它的编号。
**「不做 X」本身是活规格，不划线**——直接把标题写成否定句。

### spec 条目的固定字段

```
### S42 · 控制维度定为四项

服务   R7
规格   四项各三档，取值住在 agent YAML 的 choice.selected，改完下一轮生效
不做   单轮覆盖——取值只有一处，没有被覆盖的对象
为什么 维度越多模型越容易顾此失彼；四项是覆盖与可控的折中
验收   test_the_current_choice_lives_in_the_yaml_not_the_session
```

「不做」这一节缺席时，文档失效得最快：读的人分不清"没写"是"不需要"还是"忘了"。

## 默认流程

```
user story  →  req  →  spec + test（同时）  →  code
   你          我加工      我写，互为约束        我落地
```

1. **你给 user story。** 一句话就够，不必成形。
2. **我加工成 req**：拆成几条可验收的行为，每条配「为什么」和「不包括什么」。
3. **我写 spec 和 test，同时产出、互为约束。** 不是先写完 spec 再补测试——
   一条 spec 写不出测试就退回去重写它。这是判别式当场生效的地方。
4. **落代码，测试先红后绿。** 我会明确报出哪几条从红转绿。

### 什么时候停下来问你

**不是每条 req 都要你批准。** 只在这两种情况下停：

- **存在多方案**，且它们的取舍不是纯技术判断（影响用户看到什么、影响产品形态）
- **原文有歧义**，两种读法会导出不同的 req

其余情况我直接往下走，在交付时说明我怎么理解的。

不确定的条目**攒起来一次问**，不在中途逐条打断；但也**不静悄悄替你定**——
凭一个没说破的假设做下去，返工成本随每一步翻倍。

## 你直接改中间层时

你可以在任何一层直接动手。我的职责是**沿链向上向下各走一步**，把不一致找出来报给你。

| 你改了 | 我向上查 | 我向下查 |
|---|---|---|
| **req** | 和其它 req 冲突吗 | 服务它的 spec 逐条重读；没有 spec 覆盖 = 缺口 |
| **spec** | 它服务的 req 还成立吗？**spec 变了，req 是不是也该变** | 钉它的 test 全部重跑并重读；没有 test = 缺口 |
| **test** | 它钉的 spec 说的还是同一件事吗？**放宽断言 = 悄悄改了 spec** | 实现要不要跟着改 |
| **code** | 它实现的是哪条 spec？spec 没说的行为 = 要么补 spec，要么多余 | — |

### 三种缺口，报出来不自动补

| | |
|---|---|
| **孤儿 req** | 有需求，没有 spec 覆盖——功能缺失，或这条 req 本就不该有 |
| **孤儿 spec** | 有规格，没有 test 钉住——没人知道它现在还成不成立 |
| **野生代码** | 有行为，没有 spec 说过——**最危险的一种**，改它没人知道会碰坏什么 |

缺口是**语义判断，靠读**。曾经有一个脚本查引用一致性，后来移除了：
编号对得上不代表说的是同一件事，而一个只查编号的检查器给出的是"全都查过了"的错觉。

## 三条不随三层改变的约定

### 改 schema 必须配迁移

改了落盘数据的形状（枚举值、字段名、目录结构），**同一个改动里就要写迁移**。

漏掉的迁移不会当场报错。老数据静静躺着，直到某个读它的接口 500——而那个 500 的症状
是「新建按钮点了没反应」，离原因隔了三层。实测撞过一次。

迁移写在 `Store.migrate()` 里，服务启动时跑一次，空操作也无所谓。

### 生成物不手改

`frontend/src/protocol.ts` 由 `npm run gen:types` 从后端 Pydantic 模型生成。
改它没有意义，下次生成就没了。要改协议就改 `backend/agenttavern/server/protocol.py`
再重新生成。CI 会跑一遍生成再 `git diff --exit-code`。

### 提示词正文归用户

`backend/agenttavern/prompting/*.yaml` 里的**提示词正文是用户手写的**。
可以改这些文件的**结构**（`sections` 顺序、加一个 `choice`、改 `enabled`）和**文件头注释**，
但**不要顺手把话说得更顺**。

理由是实测出来的：有一次对照实验里"顺手把 `_CRAFT` 的一句话改得更好"，
直接让整组数据归不了因。**改提示词时"顺手把话说得更好"就是在偷偷加变量。**

## 提交前跑什么

```powershell
cd backend
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m ruff check . ; .venv\Scripts\python.exe -m ruff format --check .
.venv\Scripts\python.exe -m mypy agenttavern

cd ..\frontend
npm run lint ; npm run build
```

CI（`.github/workflows/ci.yml`）跑的就是这一串，外加生成物漂移检查。

## 这份文档管不了的

CI 挡得住的只有**机械一致性**：类型对不对、生成物漂没漂、测试红不红。

它挡不住「加了行为但没写 spec」「spec 改了代码还是老的」「测试名写成 `test_foo_works`」
——**这些全都是语义判断**。那部分靠这份文档被真的读到，没有别的办法。
