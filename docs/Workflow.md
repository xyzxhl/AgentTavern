# 工作约定

> 这份文档管的是**改动怎么落地**，不是系统怎么设计。设计判据在 [Principles.md](Principles.md)，
> 具体结论在 [Decisions.md](Decisions.md)。
>
> **主要读者是模型**（包括我自己下一次开会话时）。人也照这个来。

## 唯一的一条规矩

**规格、代码、测试，三者同时成立，或者都不动。**

这个项目没有独立的 spec 目录，规格就住在三个地方：

| 规格在哪 | 是什么 |
|---|---|
| [Decisions.md](Decisions.md) | **做什么、不做什么**，按 `D<n>` 编号。代码与测试里有八百多处引用 |
| `docs/design/*.md` | 为什么这么做、怎么权衡 |
| 测试函数名 | **可执行的验收条件**——`test_remove_on_a_scalar_deletes_the_key` 就是一条规格 |

所以"保持一致"不是抽象要求，是三条具体的触发规则：

### 改了代码 → 回头看另外两个

- 这个行为在台账里有对应的 `D<n>` 吗？**没有就新加一条**，取下一个未用编号。
- 改的行为有测试钉着吗？没有就补。测试名要写成**行为陈述句**，不是 `test_foo_works`。
- 改的是被 `D<n>` 明确规定过的行为吗？**那是在推翻一条决策**——先改台账，再改代码。

### 改了台账 → 回头看另外两个

- 被改的那条编号，`git grep -n "D<n>"` 一遍。每一处引用都要重读：它引的还是同一件事吗？
- 新决策如果规定了可验证的行为，**补一条会红的测试**。规定不了行为的（方法论、产品定位）不必补。
- **编号永不复用、永不重排。** 引用是靠编号找到规格的唯一路径。

### 改了测试 → 回头看另外两个

- 删掉或放宽一条断言，等于**放弃一条规格**。台账里有对应决策就得同步改，没有就说明这条测试当初钉的是文案不是不变量——那删得对，在 docstring 里说清楚。
- 加一条断言，等于**新增一条规格**。它对应哪条 `D<n>`？

## 台账怎么写

**直接写现在做什么、不做什么。**

不写「A 被 B 推翻、B 那半仍成立、C 又恢复了」这类相对表述。读者要先解一遍链条才知道当前规则是什么，而代码注释、测试和接手的人**都是直接拿一条当规则用**的。

| 不要 | 要 |
|---|---|
| ~~D45~~ ……**已被 D174 推翻**：…… | **不做单轮覆盖**：控制维度的取值住在提示词层（D174） |
| D36「细纲更新为实际发生的」由此落地：writer 不改写细纲 | **细纲不回写**：writer 只报告偏离（D57） |
| （D142，推翻 D60 的后半句） | （D142） |

<!-- check-decisions: on -->

**一条只讲一件事。** 若一条决策只有半截被推翻，把仍成立的那半改写成正文、把死掉的那半删掉，**而不是在标题上挂一句"前半句已作废"**。

划线（`~~D<n>~~`）只表示**整条都不再做**，保留是为了不再走回头路。它的说明先写现在的做法，再给取代它的编号。**"不做 X" 本身是一条活规则，不划线**——直接把标题写成否定句。

## 改 schema 必须配迁移

改了落盘数据的形状（枚举值、字段名、目录结构），**同一个改动里就要写迁移**，不能留到"下次再说"。

理由是实测出来的（D179）：漏掉的迁移不会当场报错。老数据静静躺着，直到某个读它的接口 500，而那个 500 的症状是「新建按钮点了没反应」——离原因隔了三层。

迁移写在 `Store.migrate()` 里，服务启动时跑一次，空操作也无所谓。

## 生成物不手改

`frontend/src/protocol.ts` 由 `npm run gen:types` 从后端 Pydantic 模型生成。**改它没有意义**，下次生成就没了。要改协议就改 `backend/agenttavern/server/protocol.py`，然后重新生成。

CI 会跑一遍生成再 `git diff --exit-code`，漂了就红。

## 提示词正文归用户

`backend/agenttavern/prompting/*.yaml` 里的**提示词正文是用户手写的**。模型可以改这些文件的**结构**（`sections` 顺序、加一个 `choice`、改 `enabled`），但**不要顺手把话说得更顺**。

理由在 D122：那次实验里"顺手把 `_CRAFT` 的一句话改得更好"直接让整组对照归不了因。**改提示词时"顺手把话说得更好"就是在偷偷加变量。**

## 提交前跑什么

```powershell
# 后端
cd backend
.venv\Scripts\python.exe -m pytest -q
.venv\Scripts\python.exe -m ruff check . ; .venv\Scripts\python.exe -m ruff format --check .
.venv\Scripts\python.exe -m mypy agenttavern

# 前端
cd ..\frontend
npm run lint ; npm run build

# 台账与引用是否还一致
cd ..
backend\.venv\Scripts\python.exe scripts\check_decisions.py
```

CI（`.github/workflows/ci.yml`）跑的就是这一串，外加生成物漂移检查。

`check_decisions.py` 判三种失败：**悬空引用**（引了台账里没有的编号）、**重号**、**引用了已划线的决策**。第三种是这份文档最容易被违反的地方——它正是"只改了三者之一"的典型症状。

**把某条决策当反面标本举例**（比如上面那张"不要/要"对照表）不是拿它当理由，用一对注释圈掉：

```
<!-- check-decisions: off -->
... 这几行里的 D 编号不算引用 ...
<!-- check-decisions: on -->
```

Python 与 TS 里写成 `# check-decisions: off` / `// check-decisions: off`。**必须显式写**——检查器不做启发式猜测，否则它迟早会自己猜掉一条真违规。

## 这份文档管不了的

CI 挡得住的只有**机械一致性**：编号存不存在、生成物漂没漂、测试红不红。它挡不住「加了行为但没写决策」，也挡不住「测试名写成 `test_foo_works`」。那部分靠这份文档被真的读到。
