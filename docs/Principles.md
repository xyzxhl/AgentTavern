# 方法与判据

> 用于做决定的判据，与具体设计分开。设计会变，这些不太会。
>
> 来源：Anthropic 关于多 agent 系统的两篇、Cognition 的两篇、Microsoft Magentic-One、Chroma Context Rot，以及本项目落地过程中的修正。文末有清单。

## 一、拆分

**P1. 上下文隔离是拆分的唯一不可替代收益。** 并行、专精都是次要收益，或可用工程手段替代。

**P2. 按跨边界信息带宽决定分解，不按工种。**

| 入参需要的上下文 | 返回的内容量 | 结论 |
|---|---|---|
| 少 | 少 | 纯工具化，无所谓 |
| 少 | 多 | 拆分的甜点区（检索类） |
| 多 | 少 | 不要拆，压缩本身就是主要失败源 |
| 多 | 多 | 切口错了，重新分解 |

一条修正：「多入少出 → 不要拆」劝退的是**无验证器的有损压缩**；可核查的压缩（如事实提取）不适用。

**P3. 操作方法：先枚举全部 context，再看某种切法下两侧是否有实质差异**（D32）。不问"该不该有某个 agent"。

**同一组工作在不同切法下结论可以相反**——见 [spec/Generation.md](spec/Generation.md)：两侧都读正文则不可分，director 只读细纲则可分。**没找到可分的切法，不等于不可分；换一刀可能就分开了。**

**P4. 区分一次性上下文与跨轮存活的上下文。** 同一份检索噪音，在一次性组件上是租用，在长期存活的组件上是买断。

**P5. 写入保持单线程。**

**P6. 反模式：按角色切分（planner / implementer / tester / reviewer）。** 实验中 subagent 花在协调上的 token 多于实际工作；"同一项工作的顺序阶段"是有问题的边界。

**P7. 无验证器的交接是预算重点。** 事实类交接可核查、漂移风险低；品味类交接错了不报警，只产出"看起来合理但不是要的东西"。

判据：一个人类主编递出这份 brief 后就走人，写手不需要追问 → 无损；写手必然回头问"你到底想要什么感觉" → 正在有损压缩品味。

**P8. 控制流与负载分布是两根轴。** tool call（控制权不转移）vs handoff（单向移交）是一根；主 agent 干活 vs 子 agent 干重活是另一根。**让子 agent 承担重任务不需要放弃 tool 语义。**

若要引入 orchestrator，其决策输入必须是**控制平面状态**而非正文，否则必然在"信息不足→决策差"和"信息充足→退化为单 agent"之间二选一。但优先级不高：若"灵活性"仅指顺序偶尔变化，带跳转的状态机更便宜、可调试、可复现。orchestrator 只在需要**基于运行时结果推翻计划**时才值得。

## 二、交给谁：模型还是代码

**P9. 能在生成前问清楚的，就不必在生成后审查。**

**P10. 凡是模型的开放判断，都降级成受约束的选择。** 目的是降低对模型能力与提示词的敏感度——开放集上的判断质量与模型能力强相关，闭集上的选择则不然。

已多次应用：不推断用户意图而用显式设置（D15）、不自由定义 schema 而是选模板或写 KV（D20/D76）、不自由判断该不该停下来问而由控制权等级给定频率（D22/D39）、输入处理收敛为三档互斥选择（D41）。

**P11. 审查类工作的增益 = 上下文差 × 验证器，两项相乘，缺一归零。**

- 上下文差为零 → 无增益。
- 无验证器 → 上下文差再大也无增益；此时审查意见只是第二种品味，改完趋向均值。
- 上游的上下文隔离未必消除上下文差：按"约束类型"切分与按"是否可核查"切分是**不同的轴**。
- **把语义判断存成结构化字段再用代码读取，不构成验证器**（D30）——字段的值本就是模型写的。

**P12. 修复成本决定能否自动强制**（D44）。补交状态增量成本≈0，可自动强制；重生成正文成本高，只能提示、由用户决定。

代码检查的主要价值在**开发期调试与 eval 采样**，不在运行时拦截（D43）：正则不是判断器，是**采样器**——把可疑样本挑出来定向送审，让覆盖率不必靠盲抽。

**P13. 规则可以做无损降维，不能做有损筛选**（D62）。分界线是**模型是否知道自己缺了什么**。

| | 合格 | 不合格 |
|---|---|---|
| 规则做什么 | 覆盖**全集**，只调节精度 | 筛选**子集**，猜相关性 |
| 失败模式 | 信息不够细 | 信息完全缺失 |
| 模型知情 | ✓ 摘要在眼前 | ✗ 不知道存在 |
| 可自愈 | ✓ 点查补救 | ✗ |

**P14. 不预设维度。** 时间、地点、角色属性的粒度与形态都取决于故事，加字段只是把猜测挪深一层（D74）。同理，不同故事需要的**能力**也不一样——关闭的能力其工具不注册（D78）。

## 三、成本与边界

**P15. 多 agent 通常比等价单 agent 多耗 3–10x token**（重编排的 research 类可达 15x）。

**P16. 每个子调用设 token 预算上限**，保证可幂等重启。

**P17. 禁止子 agent 自行再生成子 agent**——在编排层强制，不要靠 prompt 恳求。

## 四、验证方法

**P18. 先做诊断，再改结构。** 把违规按归因分类统计，各类修法完全不同，而最贵的那一类最容易被误判成下游的问题。归因五类见 [spec/Architecture.md](spec/Architecture.md)。

**P19. 消融验证。** 同一批素材跑多个配置，最少三档：

1. 单 agent 全揽
2. writer + 工具（去掉 director，细纲用人写的）
3. 完整拓扑

指标分两类：**事实/逻辑错误率**（工具层的存在理由）与**"是否写出了要的东西"**（拆分的存在理由）。后者在交互式产品里有免费的行为代理——重 roll 率、打断率、戏外引导频率。

若某一层无增益，正确动作不是删掉其功能，而是把它从"流水线上游"改为"需要时被咨询"。

**P20. 干净上下文的验证调用。** 需要判定时开新上下文，只给 [标准 + 待判对象]，不给创作过程——生成模型知道自己想怎么写，会往"已经达标"的方向读。防"过早宣告胜利"：用具体标准 + "必须完成全部检查"的显式指令。

本项目中唯一符合 P11 两个条件的场合是 goal 判定（[design/NonTurnBased.md](design/NonTurnBased.md)）。

**但"干净上下文"这一半没能守住**（D148）。goal 判定与**重拆计划**是同一次判断的两面，而重拆随时可能发生，于是它从窄调用长成了 `goal_manager`——一份跨整个 goal 生命周期的对话。保住的是"不读创作过程"：它读逐轮的结果，不读 director 怎么想的。**代价是实测可见的**：模型读的是自己写的计划、自己判的进度，比干净上下文更容易往"已经达标"的方向读——`noir_impossible` 场景下它两次把一个逻辑上不可达的目标判成 `done`，靠的是给设定编一个「诈死」的解释。P20 的"防过早宣告胜利"在长对话形态下**更难，不是更容易**。
