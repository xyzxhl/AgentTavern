# 提示词的写法与装配约定

这份文件是 `*.yaml` 的**唯一说明**。以前它散在每份 YAML 的头部注释里，四份文件
各抄一遍，改一处就有三处过时——而过时的说明比没有说明更糟。

各份 YAML 里只留**那一份文件自己的**理由（这一节为什么在这个位置、为什么给这一侧
不给另一侧），通用规则一律看这里。

**这里的东西都能在界面上改**：提示词管理页（`/agents`）。改完保存时服务端会**先
试装配一遍**，装不出来就拒绝并说是哪一节坏了（R31）。

---

## 一、一份文件 = 一个 agent 收到的**全部**文字

`director.yaml` / `writer.yaml` / `state_manager.yaml` / `goal_manager.yaml` /
`summarizer.yaml`。

**按接收方分，不按主题分。** 这样才看得出隔离有没有被破坏——文风混进 director、
正文混进哪一侧，翻开对应文件就知道。按主题分（比如「对白」一个文件）会把两侧的
内容搅在一起，而两侧的分工正是整个拓扑的地基（S3）。

**「全部文字」是字面意思**（R31）。一份文件有五个顶层键：

| 键 | 装什么 |
|---|---|
| `sections` | 它收到的那一串消息（见下） |
| `tools` | 它拿得到的工具，每个一条描述 + 开关 |
| `specials` | 运行时**另外追加的整条消息**：追加输入、空回催促、归段追问…… |
| `rendering` | 嵌在渲染里的短句：`（尚无记录）`、`用 worldinfo_read 按 ref 展开。` |
| `enabled` | 这个 agent 跑不跑（只有 `state_manager` 真的用得上） |

后三样是这次补进来的。判据是**所有被输入模型的内容，用户都能审查和修改**，而
`sections` 只是其中一部分：工具描述是模型读到的字；归段追问以前是 `postrun.py`
里一段四百多字的 Python 字符串，模型每轮都会读到而界面完全够不着；渲染文案量小
但每轮都进上下文，其中几条还是**明确的操作指令**——改了工具名却忘了改它们，
模型会去调一个不存在的工具。

**片段文件那条特例没了**：`director_append.yaml` 并进了 `director.yaml` 的
`specials.append`，装配器里「顶层直接是列表」那个分支一并删掉——它只有那一个用户。

## 二、`sections`：一个条目 = 一条消息

顺序就是列表顺序。**`role` 写在条目上。**

想调位置就移动条目，想加一节就插一条，都不用动代码——现在连 YAML 都不用开，
拖一下就行。

### 只有三类，而且 `type` 要写出来

| `type` | 用户能改什么 | 内容从哪来 |
|---|---|---|
| `text` | 正文（`body`），可含 `{{var}}` 单值占位 | 用户写的字 |
| `context` | **只有位置**（`source` 指哪一段） | 代码整段生成——世界设定、当前状态、前情、细纲、上文 |
| `choice` | 每一档的正文（`options`）**+ 当前选哪一档**（`selected`） | 用户写的字 |

```yaml
- {type: text, role: user, body: "本次目标：{{goal}}"}
- {type: context, role: user, source: worldinfo}
- {type: context, source: history}          # 一条顶多条，所以不写 role
- type: choice
  role: user
  name: speaking_rule
  selected: forbidden
  options:
    forbidden: 不要替用户的角色说话……
    allowed: 允许替用户的角色说话……
```

**类型是显式字段，不靠"出现了哪个键"去猜**：拖动排序的界面要先读出这一条是什么
类型才画得出来。

**`selected` 住在条目自己身上**（R31）。以前「有哪些档」在 YAML、「选哪一档」在
session 上，改一档文风要动两个地方；现在一处定义、一处取值、一处修改。代价是同一
台服务上两局故事不能有不同文风——那是「层级上调」的定义本身带来的。

**`{{var}}` 与 `context` 的分界是体量与位置**：前者是嵌在句子里的单值
（`用户扮演：{{user_character}}`），后者是独占一条消息的一大块。两个都要。
**变量为空就删掉它所在的那一行**，一行不剩整节就不出现——留下「视角：」这种
半截的行比没有更糟，模型会以为这里本该有内容而自己补一个。所以**一行一个变量**。

### 装配器做减法

判据是**所见即所得**：编辑器里显示的那段文字，必须就是模型收到的那段文字。
所以下面三样已经删掉（R31）：

- `title` 自动包 `<标题>…</标题>` —— 要标签就**自己写进 `body`**。
- `intro` / `outro` —— 在它前面 / 后面**放一条 `text`**，有拖动排序之后这更直接。
- `key` 引用顶层命名块 —— 它的理由是「长文本留在原处更好编辑」，有了编辑界面
  这条就不成立了；正文一律内联进 section。

**取消自动标签有一个要盯的风险**：每个 section 本来就是一条独立消息，消息边界即是
边界，所以标签在理论上是冗余的——但**部分供应商会把连续的同 role 消息合并**，
合并之后边界就没了。真出问题时的补法是**让用户自己在 `body` 里写标签**（那时它
可见、可编），不是把自动包裹加回来。

有三处**代码要认那个标签**，它们各自声明自己认的是哪一串：`specials.append.mark`
（重放时靠它认出用户的插话，保存时校验正文含它）、`rendering.flat_user_input`、
`rendering.turn`。

### 名字对不上就报错

未知的 `context`、缺值的 `{{var}}`、没写 `role`、`selected` 不在 `options` 里
——一律当场抛。**静默跳过会让一整节悄悄消失**，而产出看起来只是"变差了一点"，
那是最难查的一类问题（P29）。

顺序上还有一条约束**装配器管不了、也不该管**：`history` 之前的部分跨轮不变
（S60）。对话跨轮持续，那一段就是缓存前缀，凡是每轮会变的东西排在它前面，
缓存就永远打不中，而且旧值会以"写在最前面的权威信息"的姿态留着。

## 三、`tools`：描述可编，参数只读

```yaml
tools:
  submit_outline:
    body: 提交本轮细纲。**调用即结束这一轮**……
  history_search:
    enabled: false          # 关掉 = 根本不注册，模型看不到
    body: ……
  ask_question:             # 描述本身也可以是一个 choice
    enabled: true
    selected: medium
    options: {low: ……, medium: ……, high: ……}
```

**这推翻了 S10 ①**（工具描述不搬进 YAML）。S10 的理由是「一个工具怎么描述自己，
跟它的参数、错误信息、注册条件是同一件事，拆开写两处必然对不上」——**那个风险是
真的**，所以参数 schema 仍由 Python 生成，在页面上与描述**并排只读显示**：漂移
摆在人眼前，而不是藏在两个文件里。错误文案也仍然留在代码里，它不进上下文。

**同一个工具在两个 agent 手上是两份描述、两个开关**（`state_query` 就是）：
director 拿它是为了推演，state_manager 拿它是为了比对该改哪个键。要关就两边都关。

## 四、`specials`：运行时另外追加的整条消息

形状和 `sections` 一样，走同一个装配器，多一个 `enabled`。

| director 的 | 什么时候发 |
|---|---|
| `append` | 引导 / 打断插进来的那一条（S119②） |
| `no_input` | 没有新输入时顶上的那句 |
| `nudge` / `nudge_final` | 模型只回文本没调工具时推它一句；最后一轮换一句 |
| `converge` | 工具用完了但迟迟不收口 |
| `segment` | 生成后问它这一段收了没有（S22） |

`nudge_final` **是独立一条，不是 `nudge` 的第二档**：「这是最后一轮」和「请提交」
是两句不同的话，各自可编；做成一个 `choice` 的话「选哪一档」由代码按轮数决定，
而 `selected` 的语义是用户的选择。

## 五、`rendering`：嵌在渲染里的短句

`{{…}}` 是代码填进去的值。**每一条在代码里都有调用点，删掉会在运行时报错**，
所以保存时会逐条比对，缺了就拒绝。

**不做成一份跨 agent 的共用表，而是分到各自的 agent 名下。** `render_state` 那几句
director 和 state_manager 都会读到，于是两份 YAML 里各有一份——这不是"一件事两个
入口"：它们是发给两个不同 agent 的两条不同消息，本来就该能分别改（director 读
state 是为了推演，state_manager 读它是为了比对该记什么）。

## 六、想跑一次消融

**换一份 YAML，不是开一个 `overrides` 后门**（S80）。`lab.py` 的 `PromptSetup`
把 `prompting/` 复制到临时目录、在**副本**上改那几档、让装配器读副本，跑完删掉。
取值仍然只住在 YAML 里，bench 只是用了另一份 YAML。测试也走这一条。
