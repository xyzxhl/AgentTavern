# 提示词的写法与装配约定

这份文件是 `*.yaml` 的**唯一说明**。以前它散在每份 YAML 的头部注释里，四份文件
各抄一遍，改一处就有三处过时——而过时的说明比没有说明更糟。

各份 YAML 里只留**那一份文件自己的**理由（这一节为什么在这个位置、为什么给这一侧
不给另一侧），通用规则一律看这里。

---

## 一、一份文件 = 一个 agent 收到的全部文字

`director.yaml` / `writer.yaml` / `state_manager.yaml` / `goal_manager.yaml`。

**按接收方分，不按主题分。** 这样才看得出隔离有没有被破坏——文风混进 director、
正文混进哪一侧，翻开对应文件就知道。按主题分（比如「对白」一个文件）会把两侧的
内容搅在一起，而两侧的分工正是整个拓扑的地基（D33）。

例外是**片段文件**：顶层直接是一个 section 列表，没有命名块。`director_append.yaml`
是这一类——它不是某个 agent 收到的全部文字，而是跑到一半往对话里追加的那一条。

## 二、`sections`：一个条目 = 一条消息

顺序就是列表顺序。**`role` 写在条目上。**

想调位置就移动条目，想加一节就插一条，都不用动代码。

### 四种正文来源，写哪个就是哪个

| 来源 | 意思 | 什么时候用 |
|---|---|---|
| `text` | 正文直接写在这一条里 | **新增短提示词走这条** |
| `key` | 引用本文件顶层的命名块 | 长文本，留在原处更好编辑 |
| `context` | 系统控制的内容，由代码整段渲染注入 | 世界设定、状态、前情、细纲…… |
| `choice` | 选项组，**二级标题就是选项名** | 控制维度的档位 |

四者互斥，一条只能有一个。都没有就报错。

### `title` / `intro` / `outro`

- `title` 可选。给了就用 `<标题>正文</标题>` 包起来。
  - 用尖括号而不是 `## 标题`，因为提示词正文里本来就有 `# 核心原则` 这类小标题，
    两者长得一样时**节的边界和节内的小节分不开**。
- `intro` / `outro` 可选，垫在正文前后，同样做 `{{var}}` 替换。
  - 它们是**给 `context` 和 `choice` 用的**：那两种的正文由代码渲染或按选项切换，
    YAML 那侧本来一个字也写不进去，结果就是「世界设定」「上文」这类节光秃秃一个值，
    没有任何一句话说明该拿它干什么，而那些说明只好写回 Python 里——正是搬进 YAML
    要治的病。

### 空的整条跳过

**正文为空的条目整条不出现**，连标题、连这条消息都没有。空标题白占体量，
还会让模型以为这里本该有内容。

选项组的 `off` 档就是靠这条实现的：那一档是空串，于是整节消失。

## 三、`{{var}}` 替换

只在 `text` / `key` / `intro` / `outro` 里生效。**`context` 注入的内容不做替换**——
它是数据，用户的世界设定里完全可能出现 `{{`。

**变量为空就删掉它所在的那一行**，一行都不剩这一节就不出现。不这么做会留下
「视角：」这种半截的行——比没有更糟，模型会以为这里本该有内容而自己补一个。
**由此约定一行一个变量。**

## 四、对不上就报错，不静默跳过

未知的 `context`、缺值的变量、没给选项的组、该有 `role` 却没写——一律报错。

名字对不上说明 YAML 和代码脱节了，而静默跳过会让一整节悄悄消失，产出看起来只是
「变差了一点」。这是最难查的一类问题（D125）。

## 五、几条位置上的硬约定

### 静态前缀做成伪对话

破限一条 `system` 打头，接一条 `user` 的身份声明，再接一条 `assistant` 的应答，
此后所有静态节都是 `user`。

目的是把破限从「一段被审视的指令」变成「已经答应过的事」——模型自己说过全力配合，
后面的每一节都成了那句应答之后的追加要求。**那句应答别往下移**：它要紧跟身份声明。

### `history` 之前的都是缓存前缀（D114）

对话跨轮持续，前缀每轮不变才打得中缓存。**凡是每轮会变的东西都排在 `history`
之后**——它们本来就是这一轮的话。放前面则前缀永远失效，而且旧值会以「写在最前面
的权威信息」的姿态和新值打架。

缓存边界因此是 YAML 里可读的一条线。

### 一段 `context` 可以是一串消息

只有前情是这样：摘要和历史轮次各自带着自己的 `role`，压不成一条。
**那种条目不写 `role`**，写了直接报错——不生效的东西不该悄悄不生效。

## 六、什么不进 YAML

**轮次内只有 tool 往返和推理段**（D140）。这条线一划，「哪些提示词该进 YAML」
就不用逐个争论：

- **不进**：工具的描述、参数说明、返回文案、错误消息。一个工具怎么描述自己，
  跟它的参数、错误信息、注册条件是同一件事，拆开写两处必然对不上。
- **进**：其余每一句模型会读到的话，包括催促词、goal 的任务说明、摘要压缩指令——
  它们各自是一个 `choice` 组、带一个 `off` 档，外部因此能关掉，而不是只能改代码。

**工具清单也不进**（D149）。它走 API 请求的 `tools` 字段，模型本来就看得见；
再放一条「可用的工具」的消息，是同一份清单发了两遍。

## 代码那一侧

- `assembler.py` —— 装配机器本身，**不认识 director 和 writer**。
- `prompts.py` —— 谁收到什么，也就是 D33 那把刀：每段 `context` 注入什么、
  变量的值是什么、选项组选哪一档。

组装器管的是**这一轮发给模型的第一份消息列表**；这之后 loop 边跑边追加的东西
（模型回复、`tool_calls`、`role=tool` 结果、推理段）不归它——**那些的位置由协议
决定**（工具结果必须紧跟它的调用），编排不了，也不该编排。
